# [2510.04542] Code World Models for General Game Playing — Deep Analysis

**Date**: 2026-05-25 | **Analyst**: Paper Scout Deep Analysis Agent
**Paper**: 2025-10-06, DeepMind/Google (16 authors), 9 citations

---

## 一句话总结

LLM 将游戏规则文本翻译为可执行的 Python 世界模型（状态转移 + 合法动作 + 终止判断 + 启发式估值 + 不完全信息推理），然后 MCTS 在生成的世界模型上规划。**这是"LLM 理解游戏并生成引擎"范式的开山之作**，与我们 LLM deck prior 的愿景一脉相承但更彻底——它生成的是整个游戏模型，而非仅仅是策略分析。

## 核心贡献

1. **LLM → Executable World Model 的范式转换**：不 prompt LLM 直接出棋，而是让它写代码。生成的世界模型可验证（verify），规划器算法性地枚举合法动作，从根本上避免非法棋步——这在 GI TCG 中对应"LLM 理解规则 → 生成合法的 game engine"的构想。

2. **三层架构（Transition + Heuristic + Inference）**：
   - Transition：`step(state, action) → next_state` + `legal_actions(state) → list`
   - Heuristic：`evaluate(state) → float`（启发式估值，供 MCTS 叶子节点用）
   - Inference：`infer_hidden(state, observations) → distribution`（不完全信息下的隐藏状态推理）
   - 这个三层拆分与我们的架构惊人地对应：Inference ↔ opponent hand estimation，Heuristic ↔ GBDT value model，Transition ↔ GI TCG core 的游戏引擎。

3. **在不完全信息卡牌游戏上超越 Gemini 2.5 Pro**：测试了 10 款游戏（5 完美信息、5 不完全信息、4 新游戏），9/10 超越或持平 Gemini 2.5 Pro 的直接推理——证明 "write the game, then plan" 优于 "reason about the game directly"。

### 现状：我们已有 LLM Deck Prior（但它是 JSON，不是代码）

`@gi-tcg/llm-deck-analyzer` 是一个 4 层分析管线：
- **数据提取层**：解析 deck code → 拉取完整卡牌/角色数据（含技能描述、费用、标签、召唤物/状态描述）
- **P0-P2 启发式分析层**：7 个分析模块产出具体数值——状态依赖（`state-dependency.ts`）、有效费用（`cost-stacking.ts`）、combo 爆发窗口（`combo-clock.ts`）、抽牌期望（`draw-expectation.ts`）、资源循环（`resource-cycles.ts`）、支援区压力（`zone-pressure.ts`）、技能效率（`skill-efficiency.ts`）
- **V2 特征提取层**：产出 `DeckFeaturesV2`（dense + sparse + 30 功能标签 + 13 卡包标签 + graph nodes/edges + labels）→ 这是 GBDT ranker/value model 的实际输入
- **LLM 增强层**：启发性 baseline + 详细卡牌上下文 + 诊断问题 → LLM → 增强的 `archetype` / `planProfile` / `keyCards` / `strengths` / `weaknesses` → schema 验证合并 → 磁盘缓存

`LlmDeckPriorProvider`（`gi-agent/src/learning/features/llm-deck-prior-provider.ts`）将 LLM 分数与启发式 blended 后注入 MCTS policy context。

### CWM 与我们的差异：JSON Analysis vs Executable Code

| 维度 | CWM 的做法 | llm-deck-analyzer 的做法 | 差距 |
|------|-----------|------------------------|------|
| LLM 输出 | Python 函数（可执行） | JSON（静态描述） | 🔴 llm-deck-analyzer 生成的是**卡组的静态分析**（"这套卡组强在中期"），不是**即时态评估函数**（"当前这个具体 state 对这套卡组有利程度=0.73"） |
| 验证方式 | 执行在真实游戏上 → 测量胜率 | Schema 验证（Zod）+ 人工审查 | 🔴 没有 runtime verification——LLM 说的 strength=7.5 是否真的和胜率相关，从未被测量 |
| Heuristic 函数 | `evaluate(state) → float` | 无——`planProfile` 是 5 维静态向量（setupSpeed/tempoPush/longGameValue/defensiveStability/finisherDensity），不是 state→value 函数 | 🔴 这 5 维向量从不根据实时状态变化，MCTS 无法动态利用 |
| Inference 函数 | `infer_hidden(state, obs) → dist` | 无——完全不涉及对手手牌推断 | 🔴 完全缺失 |
| 模块化 | Transition / Heuristic / Inference 独立可替换 | 单体 JSON blob | 🟡 如果 LLM 搞错了 keyCards 的 importance，需要重新生成整个分析 |

### 直接影响？
- **CWM 不是替代 llm-deck-analyzer，而是它的下个进化阶段**。当前我们已有 "LLM reads rules → JSON analysis"，CWM 说下一步应该是 "LLM reads rules → executable evaluation function"。
- **最直接的升级路径**：在 llm-deck-analyzer 的 LLM prompt 中，除了要求 JSON 输出，增加要求：生成 `evaluate_turn_pressure(round, deck_context) → float` 的 TypeScript 函数，并用 `planProfile.tempoPush` 作为验证锚点（如果生成的函数说 "R3 aggression=0.9" 但 `tempoPush` 是 0.3，就标记为 inconsistency）。

### 方法论借鉴？
- **Exec verification 是最大缺口**：当前 LLM 输出的 `strength` / `planProfile` / `keyCards.importance` 从未被验证过——没有任何 pipeline 检查 "LLM 说 strength=8 的卡组是否真的比 strength=5 的赢得多"。CWM 的 "exec-based verification" 提示我们应该：在 benchmark 跑完后，做 post-hoc 检查 LLM 预测与实际胜率的相关性。
- **三层拆分 vs 我们的分析层**：CWM 的 Transition↔我们的 `@gi-tcg/core`（已有），Heuristic↔我们缺失（需要 runtime state→value），Inference↔我们缺失（需要对手手牌推理）。现有 7 个分析模块（combo clock / cost stacking 等）属于 "deck analysis" 而非 "game state evaluation"——它们是静态设计时分析，不是动态推理时评估。

### 不相关之处？
- **生成 transition 函数**——同前，已有 `@gi-tcg/core`。
- **多游戏泛化**——同前。
- **纯 LLM 规划模式**——同前。我们有 self-play training pipeline。

## 可落地动作（≤3 条）—— 基于实际代码校准

### 1. 测量 LLM 分析的预测效度（Existing code + 新实验）
**具体做法**：
- llm-deck-analyzer 已有 LLM 缓存（`.llm-deck-cache/`），已为多副卡组生成了 `strength` 和 `planProfile`
- 从 self-play / benchmark 结果中提取每副卡组的实际胜率数据
- 计算 correlation：LLM predicted strength vs actual win rate（Spearman's ρ）
- 计算 calibration：LLM predicted `planProfile.tempoPush` vs 实际对局中的早期进攻频率（从 replay 数据中统计）
- **如果相关性很低（ρ < 0.3）**：说明 LLM JSON 分析的 signal 太弱，需要转向 CWM 式可执行代码（下一个 action item）
- **如果相关性中等（0.3 < ρ < 0.6）**：说明现有方法有 signal 但需要改进——重点优化 prompt 和 verification
- **如果相关性高（ρ > 0.6）**：说明 JSON 分析已经足够，重点转向对手 inference 函数
- 文件位置：`packages/llm-deck-analyzer/src/evaluation/`（新建）或在 `gi-agent/src/evaluation/` 中加脚本

### 2. 原型：将 LLM 输出从 JSON 升级为 Runtime State→Value 函数（CWM-style）
**具体做法**：
- 新增 prompt variant：除了现有 JSON，要求 LLM 也生成一个 TypeScript 函数：
  ```typescript
  function evaluateGameState(
    state: GameState,
    deckContext: DeckContext
  ): {
    advantage: number      // -1..1, 0=neutral
    tempoPressure: number  // 0..1, how much pressure to apply this round
    keyCardsDrawn: string[] // which key cards have been drawn
    riskLevel: number      // 0..1, how risky is current position
  }
  ```
- 生成的函数必须通过：TypeScript 编译 → 在 10 个 snapshot states 上执行不抛异常 → 输出值在 [0,1] 范围内
- 在 `evaluateGameState` vs `planProfile` 的 consistency 上做 check（如：当 `evaluateGameState` 的 `tempoPressure` 全程 low 但 `planProfile.tempoPush` 是 0.8，标记为 LLM inconsistency）
- 集成到 `llm-deck-analyzer` 的 prompt 生成流程（`buildDeckAnalysisPrompt` 增加代码生成要求）
- 目标：不是替代 heuristic，而是作为一个**正交的评估信号源**，在 MCTS 中与 GBDT value model 加权融合

### 3. 原型：LLM opponent hand inference（新能力）
**具体做法**：
- 这是 llm-deck-analyzer 完全未覆盖的领域。参考 CWM 的 `infer_hidden` 模式
- 输入：已发生的对局 log（公开信息 + 双方 action sequence）
- LLM 任务：给定回合 R 的公开状态 → 推理对手手牌中关键卡的后验概率
- 验证：留出测试 replay，比较 predicted probability vs 实际持有率的 calibration error
- 如果成功：输出可以被整合为一个 `InferenceProvider`，在 MCTS 的 `buildMctsAction` 前注入 opponent hand prior
- 文件位置：`packages/llm-deck-analyzer/src/analysis/inference.ts`（新建）或 `packages/gi-agent/src/runtime/policy/opponent-inference.ts`（新建）

## 风险与质疑

| 风险维度 | 评估 |
|---------|------|
| **实验规模** | ✅ 10 款游戏、多种类型，但**每款游戏的复杂度远低于 GI TCG**。最复杂的测试游戏（Cheat, Stratego）有约 100-200 维状态空间，而 GI TCG 有 1000+ 维（角色 HP/能量/装备/手牌/骰子/召唤物/支援区）。LLM 能否在 GI TCG 级别生成正确的 evaluate/infer 函数，未经验证。 |
| **宣称是否过度** | ⚠️ "General Game Playing" 宣称过强。论文实际展示的是 "10-game playing"，且游戏规则都是由人类预先写成自然语言文本。这是 "language-to-game-model translation"，而非真正的 general（即从未见过的规则格式）。 |
| **LLM 依赖** | ⚠️ CWM 的正确性完全 contingent on LLM 不犯错误。论文承认 "correctness is only contingent"——如果 LLM 在 transition 函数中少写了一个合法动作，MCTS 会漏掉最优路径。在 GI TCG 中，类似的错误会表现为"LLM 误判某张牌的优先级"→ MCTS prior 偏差。 |
| **代码未开源** | ⚠️ 16 位 DeepMind 作者的论文但未发布代码。方法论详细但复现需要较强的 prompt engineering。 |
| **与 CGT 的关系** | 🟢 CWM 的 "executable formal specification" 理念与 CGT 的 "combinatorial decomposition" 高度共鸣。CGT 将游戏分解为子游戏并形式化地分析值——CWM 将游戏规则编译为形式化的代码模型。两者的交汇点是：**用代码表达游戏的形式语义**。 |

## 推荐优先级：⚠️ 本周（关键原型）

**理由**：虽然不能直接替换现有模块，但 CWM 的设计哲学（LLM 生成可验证代码而非直接推理）是我们 LLM deck prior 的**核心理念来源**。应该在 1 周内做完 heuristic value function 原型，验证"LLM 能否对 GI TCG 状态产生有用的 deck-conditioned 评估"这一核心假设。这个假设的结果会决定 deck prior 的技术路线——是继续做文本→特征（当前路线），还是转向文本→代码→执行（CWM 路线）。

**后续跟踪**：重点跟踪 DeepMind game AI 团队的后续工作——Lehrach, Hennes, Lanctot, Gemp 等人同时在 CWM 和 CSRO（2603.10098，也用到 LLM 代码生成）上工作，他们的下一个方向（可能是 CWM + RL training + multi-agent）将直接影响我们。
