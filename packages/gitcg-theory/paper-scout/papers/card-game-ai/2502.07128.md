## 一句话总结

端到端的 LLM 驱动卡牌游戏原型框架：用 graph-based 索引生成新游戏机制 → LLM 生成可执行代码 → **LLM 生成启发式函数 + self-play 优化构建 gameplay AI**，完成「创意→可玩」的原型闭环。

---

## 核心贡献（3 点）

### 1. Game Mechanic Graph — 基于图的游戏机制设计
- 从 106 个卡牌游戏描述中提取 **game mechanic graph**（节点=机制短语，边=控制流方向）
- 对节点做语义聚类（text-embedding-3-large + UPGMA），在每个 cluster 内让 LLM 生成新机制
- 对输入游戏的常见机制，用同 cluster 的新机制替换 → 生成既新颖又 coherent 的游戏变体
- 平均每个游戏提取 13±5 个节点、20±10 条边

### 2. Consistent Code Generation — 用 gameplay record 验证代码一致性
- 6 函数框架（initiation, initialize_deck, initial_dealing, proceed_round, get_legal_actions, get_payoffs）
- 创新点：不在代码级验证，而是**运行代码产生 gameplay record**，再让 LLM 判断 record 是否与游戏描述一致
- 不一致 → 定位违规规则 → 检索正确代码片段 → 修正代码 → 循环
- 结果：PCon (Play Record Consistency) 从 7.69 提升到 8.99

### 3. LLM-Generated Heuristic Functions + Self-Play Ensemble Optimization ⭐
这是与本项目最相关的部分：

- **Policy Proposal**: LLM 用 3 种 prompt 方式生成 n 条自然语言策略（strategy / game state metrics / 交叉反思），n=4 → 共 12 条
- **Heuristic Function Generation**: 每条策略翻译为 Python 函数 `Q(s, a) -> float`，只接受 game state dict + candidate action dict，返回标量分数
- **Negative Variants**: 每个有效函数 × -1 生成反向策略，总 pool = 6n = 24 个函数
- **Step-wise Inclusion Optimization**: 
  - Phase 1: 逐个测试每个 Q 函数（vs random agents, 400 games），贪心挑选 win rate 最高的加入 ensemble
  - Phase 2: 在 Phase 1 结果 + random agents 混合对手池中重复
- **Inference**: `a* = argmax_a (1/n) Σ Q_i(s, a)` — 简单的平均投票，**不需要推理时调 LLM**

## 实验结果

### Gameplay AI 性能（Table 3）
| Method | Common Games | Varied Games | All Games |
|--------|-------------|-------------|-----------|
| CoT | 1.4 ±15.8 | -4.8 ±13.4 | -0.5 ±15.0 |
| ReAct | 2.4 ±16.4 | -4.5 ±9.9 | 0.2 ±14.7 |
| Reflexion | 1.4 ±18.4 | -3.2 ±11.7 | 0.0 ±16.4 |
| Belief | 4.2 ±18.2 | -1.8 ±18.0 | 2.3 ±17.9 |
| **Ours** | **14.6 ±19.3** | **19.7 ±30.5** | **16.3 ±22.6** |

→ 唯一在 varied games 上能打败 random agent 的方法

### 消融实验（Table 7）
- ×ens（不用 ensemble，单函数）：-3.2 → **ensemble 是关键**
- ×opt（不优化选择）：0.2 → **step-wise inclusion 是关键**
- 两者同时去掉：性能降到 random 以下

### 成本分析（Figure 6）
- 由于只在生成阶段调 LLM，推理阶段是纯 Python 函数
- **50 局后总 token 成本低于所有 LLM-agent baseline**
- Reflexion 和 Belief 训练阶段的 cost 极高

### vs 人类设计的启发式（Table 6）
- Leduc Hold'em：部分配置下超过人类设计的 heuristic
- Uno：略低于人类 heuristic，但仍超过 random

### 敏感度分析（Table 8）
- n=2 时性能下降（多样性不足）
- n=6 vs n=4 无显著差异（LLM 生成策略多样性有限）

## 与我们工作的交集

### 直接影响：LLM 生成启发式函数作为 MCTS 的 value prior

Cardiverse 的核心思路可以映射到 GI TCG：

1. **Policy Proposal → LLM Deck Prior 增强**
   - `packages/llm-deck-analyzer/` 已经做了 LLM 启发式分析（P0-P2 启发式 → V2 特征 → LLM 增强）
   - Cardiverse 的做法是让 LLM 直接生成**可执行的 Python 策略代码**，而非数值评估
   - 可以借鉴：让 LLM 不生成 `strength: 7.5` 这种不可靠的数值，而是生成 Python 函数

2. **Heuristic Function Pool → MCTS Value/Rollout Policy**
   - `packages/gi-agent/` 的 MCTS 目前用 GBDT ranker + linear value model
   - Cardiverse 的 ensemble 方式可以作为 **rollout heuristic** 或 **value function prior**
   - 关键：这些函数不调 LLM，推理成本为 0

3. **Self-Play Optimization → 已有基础设施**
   - `packages/gi-agent/` 已有 self-play 管道（10-deck self-play）
   - 可以用 step-wise inclusion 代替当前的手工特征工程

### 方法论借鉴

| Cardiverse 设计 | GI TCG 可借鉴点 |
|----------------|---------------|
| 3 种 prompt 方式增加策略多样性 | 用多角度 prompt 让 LLM 生成不同的 CGT 评估策略 |
| Negative variant (-1) 增强 ensemble 多样性 | 对 CGT 的 P0/P1/P2 生成反向策略作为对比 |
| Step-wise inclusion via win rate | 用 benchmark win rate 替代手工权重调参 |
| 纯 Python 函数，推理时不调 LLM | LLM 在生成阶段用一次，推理阶段 0 token |
| 不用 fine-grained reward（指 MCTS leaf reward） | CGT 的 win/loss 信号够用，不需要 card-level reward |

### 不相关之处

- 游戏机制设计和代码生成（Component 1 & 2）与 GI TCG 无关——我们有成熟的核心引擎
- 面向「游戏原型快速迭代」，我们面向「固定游戏的最优 AI」

## 可落地动作

1. **原型实验**：在 GI TCG 上跑一遍 Cardiverse 的启发式生成 pipeline
   - 让 LLM 为 GI TCG 生成 12 条自然语言策略（strategy + metrics + 交叉反思）
   - 翻译为 Python 函数 `Q(game_state_dict, action_dict) -> float`
   - 路径：`packages/gi-agent/` 内新增 `heuristic_pool/` 目录

2. **对比评估**：LLM-generated heuristics ensemble vs 现有 GBDT ranker
   - 用 `run-benchmark.ts` 跑 head-to-head
   - 特别关注：LLM heuristics 在 varied deck（非训练集卡组）上的泛化能力

3. **混合方案**：LLM heuristics 作为 MCTS 的 prior 或 rollout policy
   - 不替代 GBDT，而是作为额外的 bias term 注入 PUCT
   - 类似 AlphaGo 的 rollout policy + value network 双轨制

## 风险与质疑

| 维度 | 评估 |
|------|------|
| **实验规模** | ⚠️ 19 个游戏，每个只有 400 局 self-play。GI TCG 状态空间远超这些简单卡牌游戏。 |
| **宣称过度** | 声称"scalable"但最高只测到 19 个游戏。varied games 标准差 30.5（vs mean 19.7），方差极大。 |
| **泛用性** | ✅ 方法本身通用——接受 game state dict → 输出 action scores。但只在回合制简单卡牌游戏上验证过。 |
| **LLM 选择** | ⚠️ 用 gpt-4o；baseline 用 gpt-4o-mini（声称性能相近但成本更低）。这对比不公平。 |
| **启发式质量** | 无独立的启发式质量评估——只测了整体 win rate。不知道单个 Q 函数是否真的学到了有意义的评估。 |
| **策略多样性** | n=4 到 n=6 无提升，说明 LLM 生成策略的多样性已饱和。可能需要更强的 diversity 机制。 |

### Step-wise Inclusion 伪代码
```
pool = [Q1, Q2, ..., Q24]  # 12 policies × 2 (正+负)
selected = []
for phase in [random_only, mixed]:
    while True:
        best_Q = argmax_{Q in pool - selected} win_rate(selected + [Q])
        if win_rate doesn't improve: break
        selected.append(best_Q)
```
