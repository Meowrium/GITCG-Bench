# LLM→专家系统方案可行性评估

> **⚠️ 状态：部分过时** — 方案 C（GBDT+PhaseStateMachine）混合架构已被采纳，但'资源线'等概念已过时。撰写于 V5。 最后审阅：2026-05-16. 见 [INDEX.md](INDEX.md)

> 评估日期：2026-05-02
> 触发问题：是否将 GBDT 打分模型替换为 LLM 生成的规则驱动专家系统

---

## 一、方案定义

```
当前：State → GBDT提取特征 → 线性组合打分 → argmax(action)
方案：State → PhaseStateMachine → DeckStrategy模板匹配 → 候选动作剪枝 → GBDT微调排序
              ↑ 阶段检测+变招触发    ↑ 人类知识编码         ↑ 骰子可行性过滤
```

**LLM 的角色**：生成 DeckStrategy 模板（角色定位、阶段计划、变招规则），运行时不再调用 LLM。

---

## 二、成功标准

| 维度 | 最低目标 | 理想目标 |
|------|---------|---------|
| **胜率 vs baseline** | >50% (8/8 卡组) | >60% |
| **镜像对局** | >50% | >60% |
| **决策延迟** | <500ms/步 | <200ms/步 |
| **卡组覆盖率** | 8/8 benchmark 卡组 | 可扩展到 40+ 卡组 |
| **版本迁移成本** | 新版本 <2周适配 | <3天适配 |

---

## 三、可行性分析

### 3.1 技术可行性：⭐⭐⭐⭐ (高)

**优势：**
- 框架文档已证明人类决策可分解为离散规则（7 节点递进）
- PhaseStateMachine 是确定性有限状态机，实现复杂度低
- 8 套 benchmark 卡组的打法在社区有充分讨论

**挑战：**
- 规则覆盖的边界情况（如双方同时触发变招条件时如何仲裁？）
- 骰子灾难恢复策略（计划完全不可行时怎么办？）
- 卡牌交互组合爆炸（30 张卡牌 × N 个角色技能 = 巨大搜索空间）

**可行性判断**：核心路径可行，但需要解决规则冲突仲裁和降级路径。

### 3.2 可扩展性：⭐⭐⭐ (中)

| 场景 | 工作量 | 风险 |
|------|--------|------|
| 新卡组（同类型） | 1-2h 编写模板 | 低 |
| 新卡组（新机制） | 需补充 PhaseStateMachine | 中 |
| 新卡牌版本 | 仅更新 CardDB | 低 |
| 新游戏机制 | 需修改状态机 + 全部模板 | 高 |
| 40+ 卡组覆盖 | 40-80h 纯手工 | 模板质量参差 |

**核心问题**：模板是手工维护的。GBDT 从数据中学习，新卡组只需跑 self-play 即可适应。专家系统每套卡组都需人工编写和调优。

**缓解措施**：
- 模板继承机制：同类型卡组复用 80% 逻辑
- LLM 辅助生成初版模板，人工校对
- A/B 测试框架：新模板定期 benchmark

### 3.3 运行时性能：⭐⭐⭐⭐⭐ (极高)

```
GBDT:  特征提取(50ms) + 推理(10ms) + 打分(5ms) = ~65ms
专家:  状态检测(1ms) + 模板匹配(0.5ms) + 候选剪枝(2ms) + GBDT排序(5ms) = ~10ms
```

专家系统在候选动作剪枝后，GBDT 只需要对 2-5 个候选打分（而非全部 20-50 个动作），显著降低推理开销。

### 3.4 维护成本：⭐⭐ (高)

```
GBDT 维护：self-play → 训练 → 部署（全自动，3h）
专家系统：编写模板 → A/B测试 → 调优规则 → 部署（半自动，3-5天/版本）
```

**版本迁移（如 v6.4 → v6.5）：**
- GBDT：跑一轮 self-play + 训练即可适配新卡牌
- 专家系统：需检查所有模板是否仍有效，新卡牌可能破坏已有 combo 逻辑

**长期维护的隐忧**：模板规则越积越多，规则间交互可能产生意外行为（emergent bugs）。

### 3.5 决策质量上限：⭐⭐⭐⭐ (高) vs ⭐⭐⭐ (不可预测)

| 场景 | GBDT | 专家系统 |
|------|------|---------|
| 标准开局 | 中等（无计划感） | 高（精确执行 PhasePlan） |
| 斩杀链计算 | 低（无搜索能力） | 高（BFS 精确算血） |
| 变招应对 | 低（无 if-then） | 高（ReplanTrigger 规则） |
| 罕见对局 | 中（泛化能力） | 低（无规则覆盖） |
| 新 combo 发现 | 低 | 无（规则已固定） |

**上限判断**：专家系统在已知场景中能达到人类水平，但在未见场景中完全依赖 fallback 规则。GBDT 理论上可以通过更多数据覆盖更多场景，但时序推理的天花板限制了它。

## 四、与其他方案对比

| 方案 | 胜率预期 | 开发成本 | 维护成本 | 泛化能力 | 推荐度 |
|------|---------|---------|---------|---------|--------|
| **A: 纯 GBDT (现状)** | 36.6% | 0 | 低 | 高 | ❌ |
| **B: 专家系统** | 55-65% | 3-4周 | 高 | 低 | ⚠️ |
| **C: 混合 (GBDT + 时序状态机作为特征)** | 50-55% | 2-3周 | 中 | 中 | ✅ |
| **D: RL 自博弈 (PPO/GRPO)** | 60-70% | 4-6周 | 低 | 高 | ✅✅ |
| **E: LLM 实时决策** | 70-80% | 1周 | 极低 | 极高 | ❌(成本) |

### 方案 C：混合架构（推荐折中）

```
不是用专家系统替代 GBDT，而是让 GBDT 的输入特征包含时序上下文：

原有特征：角色HP, 元素附着, 骰子, 手牌, ...
新增特征：current_phase(opening/midgame/closing)
         phase_progress (0.0-1.0)
         lethal_available (bool)
         dice_fitness (0.0-1.0)      ← 骰子分桶 Fitness
         opponent_last_action_type
         summon_count, support_count
```

**优势**：
- 保留 GBDT 的泛化能力
- PhaseStateMachine 提供的时序特征解决"同一状态不同阶段不同价值"问题
- 不需要为每套卡组手写模板
- 开发成本低（只改特征层，不改架构）

**预期提升**：PhaseStateMachine 特征 + 骰子 Fitness 特征 → WR 从 36.6% 提升到 50-55%

### 方案 D：RL 自博弈（长期最优）

已有基础设施（`run-self-play-rl-smoke.ts`），直接可用。RL 可以学到：
- 时序规划（通过多步 reward）
- 条件分叉（通过 policy gradient）
- 骰子管理（通过资源 reward）

**但**：RL 需要大规模 GPU 训练（远程服务器已停机），本地 i7-7700HQ 训练一轮需 2.5h。

## 五、风险评估

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 模板无法覆盖所有对局 | 高 | 中 | fallback 到 GBDT |
| 规则冲突导致行为异常 | 中 | 高 | 规则优先级 + 冲突检测 |
| 新版本适配周期长 | 中 | 高 | LLM 辅助生成模板 |
| 专家知识偏差（模板不优） | 高 | 中 | A/B benchmark 验证 |
| GBDT 退化（剪枝过激） | 低 | 中 | 保留完整候选池作为 fallback |

---

## 六、建议路线

```
Phase 1 (1周)  → 方案 C：GBDT + PhaseStateMachine 时序特征
                  投入最小，验证"分段特征"是否能突破 50%
                  
Phase 2 (条件) → 如果 Phase 1 达不到 50%：
                  启动 方案 B 的模板编写（先从 HongNiu 和 MoYou 试点）
                  
Phase 3 (长期) → 方案 D：RL 自博弈替代 GBDT（当远程 GPU 可用时）
```

**当前推荐：先做方案 C**。理由：
1. 代码改动最小（只改 `gi-ml-policy.ts` 的特征提取）
2. 如果有效 → 证明了"分段信息是关键"，后续可以用 RL 学习更优的分段策略
3. 如果无效 → 说明问题更深（GBDT 架构本身不适用），再转向专家系统

---

## 七、结论

| 问题 | 答案 |
|------|------|
| 专家系统技术上可行吗？ | ✅ 可行，8 套卡组范围可控 |
| 能规模化吗？ | ⚠️ 可以但维护成本高（O(N) 卡组数） |
| 比 GBDT 更好吗？ | 在已知场景更好，泛化更差 |
| 应该现在做吗？ | ⚠️ 先试方案 C（低成本验证），再决定是否全量 |

**核心判断**：专家系统在当前 8 套卡组 benchmark 的封闭环境中是最优解，但它的上限被手工维护限制。建议先用**方案 C（混合特征）**低成本验证分段信息的价值，如果效果显著，说明方向对，再决定是继续手工模板还是转 RL 自动学习分段策略。
