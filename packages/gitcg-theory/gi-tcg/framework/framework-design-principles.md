## 框架设计原则（v1）

> 来源：与资深玩家 5 轮 Q&A 后归纳。这份文档不展开技术细节，只固定**对照标准**——
> 用于判断后续 framework 各项决策是否一致、用于把开放问题快速收敛、用于发现现有文档中的矛盾。
>
> 五条原则按重要性递减排列；序号即引用代号（P1-P5）。后续文档应直接引用 `(P1)` / `(P2)` 等。

---

### P1 · 决策单位主导拆分

> **AI 框架的拆分粒度 = 玩家级独立决策的最小单位。**
> 引擎事件如果**不构成独立决策**（只是母决策的自动副产物），就合并到母决策的数值里；
> 引擎事件如果**构成独立决策**（玩家需要单独考虑"何时做 / 做不做 / 做哪种"），必须单列。

判别问句：「该事件是否带来一个**独立的、跨多步的玩家选择**？」
- 是 → 单列子项 / 单列 candidate family / 单列资源轴。
- 否 → 合并到上层评估数值。

**典型应用**：
- ✓ 单列：免死耗尽（"何时打掉它"是独立决策）、调和的 `tuningTarget`（决定下一步 cost）、LEGEND/秘传的"整局一次"机会成本、被击倒后的 `chooseActive`、出战角色（决定 ALIGNED 解锁哪些手牌）。
- ✗ 合并：反应直接增伤 +2/+1（跟随母技能决策，无独立选择）、引擎的 modifyDamage 0/1/2/3 四段、safe/critical 二段管线、月相反应（玩家不能在普通/月相之间二选一）。

**辅助判别**（用户补充）：「事件影响的时间跨度远超当前动作」→ 倾向单列。但跨度量化困难，仅作辅助。

### P2 · AI 结构 ≠ 引擎结构

> **引擎按"游戏机制的因果链"组织；AI 按"玩家可决策的窗口"组织。两者结构差异的部分，AI 框架不需要还原。**

这是 P1 的补充：P1 给出"何时拆 / 何时合"，P2 给出"沿着哪条线拆"。

具体含义：
- 引擎做了区分但 AI 不需要区分 → **简化合并**。
  - 例：`modifyDamage0/1/2/3` 四段、`safeDamage/criticalDamage` 二段管线、`onBeforeUseSkill/onUseSkill` 时序、月相反应白名单——这些都是引擎执行因果，玩家视角看不见也用不上。
- 引擎没区分但 AI 必须区分 → **显式建模**。
  - 例：迪希雅"已开战技 vs 未开战技"的功能层级跳变（引擎只看 alive=1）；同一角色不同回合的 `K_kill` 系数衰减；击倒后 `chooseActive` 与主动 `chooseActive` 的**战术语义等同**（引擎是不同 RPC，AI 应同类决策点处理）。

判别问句：「这条引擎区分对**玩家做这一步选择**有用吗？」
- 有用 → 保留。
- 无用 → 合并 / 屏蔽。

### P3 · 评估与执行同粒度

> **评估端（value head / V(s)）和执行端（policy head / ranker）使用相同的特征粒度。
> 双视角的差异只在"对方私有信息能否看到"上（`debug_full` vs `policy_public`），不在"看到的字段精细程度"上。**

含义：
- 不允许「评估端用引擎事件粒度（每次 modifyDamage 都看见），执行端用玩家直觉粒度（只看伤害总值）」这种分裂——会导致 V 学到的东西无法被 policy 调用。
- 评估端预测的"未来胜率"必须基于执行端实际能感知的同一组特征。
- `debug_full` 视角只用于训练时的对照、上界分析、数据增广；**不允许**生产策略依赖它。

判别问句：「这条特征如果只在评估端有，policy 能从输出反推它吗？」
- 能 → 不必双视角。
- 不能 → 必须同时进 policy obs，否则不要进 value obs。

**典型应用**：
- 信息差异（对方手牌等）允许双视角分裂；
- 计算精度差异（V 用真伤、policy 用启发伤）禁止；
- `causeDefeated`、`canCharged` 等合法动作前置量必须进 `policy_public`，否则 policy 看到的合法集会失真。

### P4 · 知识源优先级：决策时 S3 > S1 > S2，引导期反向

> **决策时（已训练好的模型在线推理）**：
> 数据驱动学习（S3） > deck-aware 模板（S1） > 玩家级元规则（S2）。
> **引导期（S3 尚无数据可用）**：
> S2 先行，S1 跟进，S3 在前两者基础上学习并最终接管。

三种知识源的定义：
- **S2 玩家级元规则**：跨卡组通用启发式。"能量满前保护核心角色"、"反应链已铺要触发"、"3→2 角色后切策略模式"、"先调和后行动"。
- **S1 deck-aware 模板**：单卡组的胜利路径、关键组件清单、阶段触发器、条件路径分支。由人或 LLM 手写。
- **S3 数据驱动**：RL / GBDT 从对局数据里学到的精细模式。

为什么决策时 S3 > S1 > S2：
- **特异性递增**：S3 见过的是具体局面对应的具体收益，S1 是 deck 级方案，S2 是跨 deck 的最一般启发——越具体的知识在该具体局面上越准确。
- **资深玩家直觉一致**：人类高水平玩家做决策时也是"训练出的对局直觉（≈ S3） > 该套牌的胜利计划（≈ S1） > 通用打牌原则（≈ S2）"，而不是反过来。
- 当 S3 与 S1/S2 矛盾时，**信任 S3**（前提：S3 在该 matchup/局面有足够样本支持）。S1/S2 退化为安全网（兜底 + 可解释性来源 + 数据未覆盖区的 fallback）。

为什么引导期反向：
- 训练初期 S3 没有数据可学，必须用 S2 / S1 提供先验、塑造样本分布、定义 reward shaping。
- 第一版 RL 的 reward / GamePlan / shaping 项都按 S2 优先编码，原因是工程必要性，不是知识价值优先级。
- 一旦 S3 在某个 matchup 上达到稳定（评测胜率收敛、决策一致性 OK），就允许 S3 在该 matchup 上覆盖 S1/S2。

判别问句：「这条决策**当前是 S3 数据足以支持**的吗？」
- 是 → 听 S3。
- 否 → 回退到 S1（如果有模板覆盖），再回退到 S2。

**典型应用**：
- T_now / T_plan 的子指标在 deck 间共享（S2 引导启动），权重最终由 S3 学（决策时由学到的权重主导）；
- GamePlan 模板由 LLM/玩家手写（S1 引导填充），但 S3 的 ranker 输出可在线覆盖模板的 candidate 排序（信任 S3）；
- 反应窗口、爆发窗口、3→2 坍缩等都属于 S2 兜底；S3 学到的"该 deck 的爆发应该在 R3 而不是 R2"会覆盖通用的"满能量就开"；
- 自对弈数据中发现"开局直接打技能比铺装备好"——若 S3 数据稳定且 matchup 一致，**该局面下相信 S3**；同时检查 S2 元规则是否需要细化（不是直接推翻 S2，但允许在该局面绕开）。

**反例（违反 P4）**：
- 决策时强行用 S2 元规则覆盖 S3 学到的精细模式（"模型选了 X，但启发式说应该选 Y，听启发式" → 浪费学习成果）；
- 引导期就尝试让 S3 覆盖 S1/S2（数据不足时 S3 学到噪音，反过来污染训练）。

### P5 · 连续价值 + 多路径并行评估，禁止过早分类

> **AI 用单一连续价值函数 `V(s) ∈ ℝ` 评估局面，对一个局面**并行**评估多条潜在胜利路径（保命 / 斩杀 / 资源消耗 / 节奏压制），决策取 max 或加权和。
> **禁止**先把局面分类到某个"模式"再类内打分。**

理由（用户原话）：「看起来快输的局可能可以马上杀完对面，决策模式的语义可能局限性比较大。」

含义：
- 不允许 `mode_classifier(s) → mode-specific evaluator` 的两段架构；
- 不允许"按存活角色数路由独立模型"（3→2→1 三个独立模型）；
- 不允许"按 archetype 路由"（aggro / control / midrange 三个独立 evaluator）。
- 离散阈值（能量满、HP < 斩杀线、召唤物计数到位、3→2 坍缩）只能作为**输入特征**，不能作为**路由器**。
- 多路径并行评估的工程化落地：让 `V(s)` 把不同路径的潜力都吸收到同一个标量里，或在 ranker 候选打分阶段并行计算 `Q_path_kill / Q_path_attrition / Q_path_setup`，最终取 max。

判别问句：「这条架构会让某个反直觉但可能成立的路径被砍掉吗？」
- 会 → 拒绝。
- 不会 → 接受。

**典型应用**：
- ✓ V(s) 由非线性模型（GBDT / MLP）输出实数，离散阈值进 feature；
- ✓ candidate ranker 并行打多路径，policy 取 max；
- ✗ 按存活数路由独立模型；
- ✗ 阶段感知改成"先判定 setup / execution / closing 再走对应 evaluator"；
- ✗ archetype-aware 多 head 路由。

## 原则之间的交互

| 场景 | 主导原则 | 次主原则 |
|------|---------|---------|
| 决定要不要拆出某个子项 | P1 | P2 |
| 决定特征是 obs 字段还是 derived 字段 | P3 | P1 |
| 知识冲突（模板 vs 模型） | P4 | — |
| 引入新的"决策模式"或"局面分类" | P5 | P2 |
| 已经在引擎里区分但理论里要不要还原 | P2 | P3 |
| 跨卡组共享 vs deck-specific | P4 | P1 |
---

## 原则的反例（提醒：以下做法违反原则，应避免）

- **违反 P1**：把"反应类型"作为 candidate family 之一暴露给 policy（玩家不能"打反应"作为独立动作，反应是技能的副产物）。
- **违反 P2**：在 obs 中记录每段 modifyDamage 的中间值（引擎结构无关玩家决策）。
- **违反 P3**：value head 用真伤计算，policy head 用启发伤估计——会导致 V 学到的"危险局面"在 policy 视角下根本看不到。
- **违反 P4**：决策时强行用 S2 元规则覆盖 S3 学到的精细模式——浪费学习成果，也违背"具体局面具体判断"的玩家直觉。或反向：引导期 S3 数据不足时就让 S3 接管，导致噪音模型污染训练。
- **违反 P5**：用 `if 存活角色数 == 2: load model_2v2` 这种路由——会让"3 角色逆风一波斩杀"和"2 角色拖延翻盘"两条路径无法在同一个评估器里被对比。

## 后续如何使用本文档

1. 任何新增 framework / RL contract 提案，自检 P1-P5 是否一致。
2. `framework-deepening-questions-for-expert.md` 中标记了"参考答案（基于 P1-P5 推导）"的问题，玩家审阅时只需检查"原则是否被正确套用"，无需重新推导。
3. 提问册已全部作答，所有**已收束结论**汇总在 `framework-resolved-decisions.md`（按 §0-§十 + 待议 TODO 表），作为重写 `framework.md` / 落地 `rl-implementation-spec.md` 的权威输入。
4. 若发现某个原则与新观察明显矛盾，**先修原则**（写新版本 v2），再批量审视下游决策。
5. 现有文档中违反原则的地方，列入 `framework-revision-todo.md`（待建）。
