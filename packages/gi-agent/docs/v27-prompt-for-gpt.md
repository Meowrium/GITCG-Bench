## 项目背景

### 我们在做什么

为《七圣召唤》（Genius Invokation TCG）构建 AI 决策系统。当前架构：

```
游戏状态 → GiMlPolicy（10+ 启发式信号线性叠加）
         → SlotLinearRanker / GBDT Ranker 打分
         → 选最高分动作
```

核心组件：
- **Ranker**：对候选动作打分（当前用 LightGBM lambdarank，NDCG@1 ≈ 0.31-0.34 per-deck）
- **Value Model**：评估局面价值（Linear / GBDT）
- **MacroPlan**：LLM 生成的回合级计划，给候选动作加权
- **TemporalOpportunityModel**：时序机会评估（支援牌部署、召唤物节奏等）
- **MCTS**（实验性）：用 ranker 分数做 PUCT prior，深度 3-5 搜索

### V25 结论：线性信号叠加已达极限

最近实验（V25，8 套卡组 self-play + per-deck GBDT ranker）的核心发现：

1. **隐式卡组编码假说被拒绝**：统一 ranker（不给 deck-id 特征）训练的模型，在镜像对局中 WR 跨度 20%-80%（StdDev=21%）。不同卡组对同一 ranker 的理解差异巨大。

2. **per-deck ranker 可行但不够**：每个卡组独立训练 GBDT ranker（NDCG@1 0.31-0.34），但仍有大量"明显错误"的决策——不是因为评分不准确，而是因为评分框架本身有结构缺陷。

3. **根因：当前框架假设"每个动作的 value 可以独立评估"**。实际上，动作价值取决于它对后续回合的影响——骰子消耗的机会成本、元素附着的连锁反应、支援位的边际效用。

## 难题一：Transition-based 决策范式的形式化

### 问题陈述

当前 GiMlPolicy 的评分公式（简化）：

```
score(action) = Σ w_i · signal_i(action, state)
```

每个 signal 是"当前状态下这个动作的某个属性"（如 `is_elemental_skill`、`reaction_value`、`dice_efficiency`）。

**核心缺陷**：这套框架无法表达"这个动作会如何改变局面，以及局面变化带来的价值"。

举例：
- **骰子稀缺**：消耗 3 个同色骰打技能，表面看 `dice_efficiency` 正常。但如果下回合需要 8 个同色骰打 burst，当前消耗会锁死后续选择。
- **元素附着债务**：给对手挂水元素可能是"正确"的动作（触发感电），但如果对手场上有雷系角色准备切上来，挂水实际上在帮对手。
- **支援位边际价值**：第 1 个支援位和第 4 个支援位的价值完全不同，但当前模型只看到"部署支援 +X 分"。

### 需要形式化的内容

请给出一个 **transition-based 评分框架** 的数学定义：

#### 1.1 State 表示

定义"局面状态"的数学结构 `S`，使得：
- 从 `S` 出发可以计算任意动作 a 的后继状态 `S' = T(S, a)`
- `S` 足够紧凑，能在 MCTS 的每次模拟中高效计算
- `S` 包含：骰子分布、元素附着图、角色血量/充能、支援/召唤物位、手牌、先后手、轮次

#### 1.2 Transition 算子

定义 `T(S, a) → S'`：
- 如何从当前引擎状态快速投影到 `S`？
- 哪些细节可以省略（"轻量投影" vs "完整引擎模拟"的折衷）？
- 如何保证投影后的 `S'` 在关键维度（血量、充能、元素附着）上与原引擎一致？

#### 1.3 Transition Value

定义 `V_T(S, a) = V(S') - V(S)`：
- 如何训练/计算 `V(S)`？（能否复用现有 GBDT value model？需要哪些额外输入特征？）
- 如果 `V(S)` 不完美，如何量化 `V_T` 的置信区间？
- `V_T` 如何与现有的 ranker 分数融合？（加权和？乘性门控？）

#### 1.4 与现有系统共存

关键约束：**不能推倒重来**。当前有投入大量工程努力的 ranker、value model、self-play pipeline。新框架必须：
- 能在现有 GiMlPolicy 中以"附加评分组件"的形式接入
- 不破坏现有的 self-play → 训练 → benchmark 循环
- 可以逐步迁移，先用于少数决策点，验证有效后再扩展

### 期望输出

1. **数学定义**：`S`、`T(S,a)`、`V_T(S,a)` 的形式化定义（带类型签名）
2. **计算复杂度分析**：每个候选动作的 `T` + `V_T` 计算开销
3. **接入方案**：如何在 GiMlPolicy 的 `score()` 函数中加一个 `transitionDelta` 项
4. **可证伪验证**：什么实验能证明 transition-based 确实优于线性叠加？（建议实验设计）

## 难题二：9 个隐藏约束的数学形式化

### 问题陈述

我们识别了 9 个当前架构忽略的"隐藏约束"，每个对应一类系统性决策失误。当前它们只是文字描述，需要转成可计算的数学函数。

### 九个约束

#### H1：行动权约束

`declareEnd` 不是普通动作。它改变：
- 当前回合剩余行动权（我方结束后对手可继续行动）
- 免费切换窗口（我方 declareEnd → 对手获免费切人机会）
- 下轮先手权

**需要**：`ActionRightsDelta(a, S)` — 动作对行动权的改变量

#### H2：骰子稀缺元素

骰子价值不是总数的函数。消耗 3 个火骰的价值取决于：后续回合是否需要火骰、需要几个、是否有替代方案（万能骰/元素调谐）。

**需要**：`DiceOpportunityCost(a, S)` — 消耗特定骰子对未来动作集合的影响

#### H3：元素附着债务

施加错误的元素附着会破坏后续反应链。需要区分：
- 建立 aura（给对手挂元素，主动）
- 消费 aura（触发反应，有利）
- 覆盖/清除 aura（可能有利也可能有害）

**需要**：`AuraDelta(a, S)` — 元素附着状态变化 + 对潜在反应链的影响

#### H4：支援/召唤位边际价值

4 个支援位的价值非线性：
- 第 1 个支援：从无到有，价值最高
- 第 4 个支援：挤满位置，价值为负（除非替换价值更低的支援）
- 替换已有支援：价值 = 新支援 TV - 旧支援剩余回合价值

**需要**：`SupportSlotValue(a, S)` — 考虑位满/替换情况的实际边际价值

#### H5：角色功能完整性

同一卡组的 3 个角色功能不同：
- 核心输出（承担主要伤害，应保护）
- 挂元素工具人（进场挂元素后切走，血量不重要）
- 保护对象（需保持血量以阻挡对手斩杀）

**需要**：`DeckRoleProfile(deck)` — 从卡组构成自动推断角色功能，输出每个角色的 `risk_weight`（血量损失的单位代价）

#### H6：对手 cashout readiness

我方动作的价值取决于对手下一/两动能否兑现威胁：
- 对手充能满 → 下动可能 burst（伤害翻倍）
- 对手场上有火+水角色 → 可能切人打蒸发
- 对手手牌多 + 有 dice → 可能打出关键 event 牌

**需要**：`OpponentThreatVector(S)` — 对手当前可兑现的威胁及其概率

#### H7：先后手与轮次节奏

同一动作在先手和后手价值不同：
- R1 先手攻击作用：迫使对手响应（用掉 dice 防守而非部署），而非直接伤害
- 后手 declareEnd 的风险低于先手

**需要**：`RoundTempoMultiplier(a, S)` — 考虑先后手和轮次的节奏修正因子

#### H8：手牌 option retention

元素调谐需要消耗手牌。不同手牌的"保留价值"不同：
- 消耗第 3 张相同的低费 event 牌 → 机会成本低
- 消耗唯一的关键 talent 牌 → 机会成本极高（后续 combo 无法触发）

**需要**：`HandRetentionValue(card, deck)` — 每张手牌的保留价值，`TuningCost(a, S)` — 元素调谐实际代价

#### H9：随机性与隐藏信息

模型容易把公开状态当完整状态：
- 对手手牌中的隐藏斩杀组件
- 我方的抽牌期望（还没抽到的关键 combo 牌）
- 骰子重投的随机性

**需要**：`HiddenInfoRisk(S)` — 用风险区间（[lower_bound, upper_bound]）而非点估计来修正决策

### 期望输出

对每个约束 H1-H9，给出：

1. **数学定义**：输入、输出、核心计算逻辑
2. **特征依赖**：需要从游戏引擎提取哪些数据？
3. **复杂度**：每个候选动作的计算开销
4. **独立性**：能否独立验证？（不需要等其他约束实现）
5. **优先级建议**：按"可实现性 × 预期改进"排序

## 特别提醒

1. **不要泛泛而谈**。需要具体的数学公式、类型签名、计算步骤。不是"应该考虑骰子机会成本"，而是"骰子机会成本 = Σ_{后续需要此色骰的动作} P(该动作最优 | S') × 所需骰数 × 权重"。

2. **不要忽略现有系统**。新方案必须能接入 GiMlPolicy 的 `score()` 函数中，作为一个可开关的组件，不能要求重写整个评分框架。

3. **给出可证伪预言**。每个方案附一个具体的实验："如果方案 X 正确，我们应该在 Y 类对局中看到 Z 现象，否则方案 X 不对"。

4. **数理优先**。优先给出数学上正确、优雅的建模，工程实现细节可以简略。
