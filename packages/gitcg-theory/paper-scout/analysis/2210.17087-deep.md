# [2210.17087] DanZero: Mastering GuanDan Game with Reinforcement Learning — Deep Analysis

**Date**: 2026-05-25 | **Analyst**: Paper Scout Deep Analysis Agent
**Paper**: 2022-10-31, 5 authors, trained 30 days on 160 CPUs

---

## 一句话总结

DanZero 是少数真正把大规模分布式 RL（160 CPU、30 天）用于复杂卡牌游戏（掼蛋——比斗地主更复杂的 4 人竞争/合作混合游戏）并达到人类水平的工作——它是对我们 GI TCG 训练基础设施最直接的**规模参照系**。

## 核心贡献

1. **分布式 Self-Play at Scale**：160 个 CPU actor 并行生产训练样本，1 个 GPU learner 做 Deep MC policy 更新——这是卡牌游戏 RL 领域**公开记录中最大的训练集群之一**。我们的 GI TCG 自对弈（16C 60GB 阿里云 ECI Spot + 10 decks）在规模上差了 10-40 倍。

2. **Deep MC 的工业级实现**：不依赖 tree search（没有 MCTS），纯粹的 Monte Carlo rollout → bootstrapping-free value target。方法论简单但**工程规模弥补了方法简单性**——当样本量足够大时，Deep MC 的方差问题被大量样本吸收。这对理解"我们是否真的需要 MCTS 树搜索"有关键参考价值。

3. **Human Evaluation**：不仅和 heuristic baseline 比，还和真实人类玩家比——这在 RL 论文中很少见。他们的评估框架（rating 系统、盲测、统计显著性）比纯 self-play Elo 更可信。GI TCG 目前没有系统化的人类评估。

## 与我们工作的交集

### 直接影响？
- **TRAINING INFRASTRUCTURE REFERENCE**：DanZero 的 160 CPU → 我们的 16C ECI Spot。如果我们想 scale 到 10x 卡组数或 10x 训练步数，需要考虑类似的分布式架构。当前 `run-self-play.ts` + `self-play-collector.ts` 是单机设计，**没有跨节点协调能力**。

### 方法论借鉴？
- **Deep MC vs MCTS 的 tradeoff**：DanZero 是 "Deep MC wins at scale" 的关键证据——当样本量足够，Deep MC 的无搜索 rollout 可以达到 human-level。这引出一个关键问题：**我们的 MCTS 在 200 iterations 的搜索深度是否能超越"等量算力投入 Deep MC 更多 rollout"的效果？** 这个 tradeoff 从未在 GI TCG 上被测量。
- **State feature engineering**：DanZero 针对掼蛋手动设计的状态特征（卡牌编码、剩余牌估计、搭档信息编码）展示了复杂卡牌游戏的 feature engineering 方法论。我们的 slot-linear features（`slot_linear.py` 中的 slot groups）可以参考这种"游戏特定但通用设计模式"。
- **Actor-Learner decoupling**：DanZero 的 actor 和 learner 是完全解耦的（actor 写 replay buffer，learner 读），与我们的 self-play → dataset → batch train pipeline 在架构上相似但实现不同（我们用的是 batch offline，DanZero 是 streaming online）。

### 不相关之处？
- **4 人竞争/合作混合**——掼蛋是 2v2 合作竞争，GI TCG 是 1v1。合作推理（搭档信号、出牌协调）在 GI TCG 中没有对应。
- **掼蛋特有的卡牌机制**——点数 + 炸弹 + 组合出牌（顺子/对子/三带二等）与 GI TCG 的技能/召唤/支援/反应的系统完全不同。特征设计的具体内容无法移植，但设计方法论（"如何将复杂游戏状态编码为 flat vector"）通用。
- **2022 年 pre-LLM era**——DanZero 不涉及任何 LLM 组件。我们的 LLM deck prior 是完全独立的研究方向，不会从 DanZero 获取灵感。

### 1. 测量 MCTS vs DeepMC 的效率 tradeoff（本周可启动）
**具体做法**：
- 实验设计：固定总推理算力（如 1 秒思考时间），对比：
  - MCTS (200 iterations, depth=6) — 当前配置
  - MCTS (100 iterations, depth=3) — 轻量配置
  - DeepMC (1 秒内做尽可能多的 rollout, no tree search) — DanZero 模式
- 使用 `packages/gi-agent/src/evaluation/branch-eval/` 框架
- 评估指标：win rate, decision time, decision quality（对比更深的 MCTS 的 top-1 action agreement）
- 目的：验证"300M 样本级联的 DeepMC 是否优于 200-iteration MCTS"

### 2. 扩展 Self-Play 的分布式训练能力（下周设计）
**具体做法**：
- 当前架构：`self-play-collector.ts` 在单进程/单机运行（16C ECI），生成训练数据 → `train_lgbm_value.py` / `train_slot_linear_ranker.py` 做离线 batch 训练
- 扩展方向（DanZero 风格）：多个 ECI Spot 实例并行运行 actor，写入共享 replay buffer（Redis/OSS），单 GPU learner 读取训练
- 第一步：撰写 `docs/design/distributed-self-play.md`，评估成本（ECI Spot × N 实例）与收益（样本量 × N）
- 注意：我们的训练是 offline batch pipeline，与 DanZero 的 online streaming 不同。转型成本需要考虑

### 3. 建立 Human Evaluation Protocol（本月设计）
**具体做法**：
- DanZero 的 human evaluation 是 systematic 的（rating system + blind testing + statistical tests）
- 为 GI TCG 设计类似协议：
  - 招募玩家（内测群 / 社区）
  - 盲测设计：玩家不知道对手是人类还是 AI
  - 赛后问卷：对手的"人感"评分（Turing test light） + 决策质量评分（1-5）
- 对比：当前 benchmark 只测 AI vs AI 的 Elo，缺少 AI vs Human 的性能锚点

## 风险与质疑

| 风险维度 | 评估 |
|---------|------|
| **实验规模** | ✅ 160 CPU × 30 天是大规模训练，但**这与我们的约束严重不匹配**。我们在 16C ECI Spot 上运行（约 $0.5-1/hr 竞价价格）。160 CPU 按同等比例约 $5-10/hr，但 30 天 = $3600-$7200，这对个人/小团队是显著的。如果我们不能 match 这个 compute 规模，DeepMC 在我们的场景中可能不会同样有效。 |
| **宣称是否过度** | 🟡 "Human-level performance" 需要看对手水平。论文对比的是 casual 掼蛋玩家（非专业），而我们面对的 GI TCG 顶级玩家可能有显著更高的 skill ceiling。Human-level for casual ≠ human-level for competitive。 |
| **Deep MC 的方差问题** | 🔴 在掼蛋中，一局可以很长（几十到上百轮）且每轮的随机性相对可控（只有发牌）。但 GI TCG 的回合数是固定的（~15 rounds）且每轮有骰子随机（8 面骰 × 8 元素 = 大量随机）。Deep MC 在短 episode + 高方差的游戏中容易受 variance 影响——这是 MCTS 的 tree search 优势所在（通过子节点聚合减少方差）。 |
| **与 CGT 的关系** | 🔴 无。DanZero 没有涉及任何组合博弈论或形式化游戏分析。Deep MC 是纯黑盒 MC 方法，不做任何游戏特定剪枝或分解。这和我们的 CGT-enhanced MCTS 形成对比——我们需要理解哪些 CGT 优化在 scale 足够大时可能是 unnecessary 的（但可能在小样本制度下是关键的）。 |
| **代码未公开** | 🔴 无代码。分布式训练架构的描述是 high-level 的，实际工程细节（actor-learner 通信协议、buffer 管理、fault tolerance）需要从零设计。 |

## 推荐优先级：📅 存档（Infrastructure reference）

**理由**：DanZero 是重要的规模参照系和分布式训练蓝本，但在**当前阶段**（我们仍在做算法验证和 CGT 原型，而非 scaling bottleneck）不需要立即行动。MCTS vs DeepMC 的 tradeoff 测量是低成本高价值的实验（可以本周用现有 branch-eval 框架跑），但真正的分布式 self-play 扩展应该在以下条件满足后再启动：
1. 单机 16C 上的自对弈 pipeline 已经稳定（收敛曲线清晰、超参数 tuned）
2. MCTS 的 CGT 优化（P0-P3）已经验证并在单机上展示出足够的 win rate gain
3. 瓶颈明确落在"样本量不足"而非"算法质量不足"

**后续跟踪**：跟踪 "distributed RL for imperfect information games" 方向的最新进展（DeepNash, R2D2, IMPALA 的 adaptions for card games），研究 actor-learner 通信开销优化（特别是跨节点 scenario 下的样本压缩）。
