# 七圣召唤框架

> 目标：先建立一套足够普遍的概念框架，用于整理七圣召唤 AI 设计中最关键的状态表示、搜索困难与价值评估问题。  
> 用途：先服务于整理思路，后续用于指导 LLM 或程序实现继续细化。  
> 参考：
> - 卡牌信息：`genius-invokation/packages/data/src`
> - 卡组代码解码：`genius-invokation/packages` 下的 `decoder` 组件

## 一、本文想回答什么

本文不是直接给出一个可运行的算法，而是试图解释以下问题：

- 为什么七圣召唤的搜索空间巨大且难以化约。
- 为什么真正有实战价值的展开轴在全部合法操作序列中极其稀疏。
- 为什么静态伤害值不足以表达一个操作的真实收益。
- 为什么低血量角色的风险需要被显式建模，而不能只看剩余血量。

更进一步地，本文希望说明：七圣召唤中存在广泛的长程结构。很多看似可以接受的局部最优决策，会在后续的非线性联动中被放大为显著损失。因此，仅靠局部指标进行近视优化，通常不足以支撑强度足够的 AI 决策。

## 二、`def 0. 状态`

记状态为 `s`。七圣召唤中的状态，指的是全部会影响后续合法操作与价值判断的对局变量，至少包括：

- 角色相关信息：血量、能量、出战状态、站位、装备、角色状态、出战状态。
- 场上公共区域：支援区、召唤区。
- 资源信息：骰子、手牌、牌库，以及卡牌附属状态。
- 流程信息：行动权归属、当前阶段。

七圣召唤是**非完美信息博弈**，因此需要区分：

- 对局的真实状态。
- 玩家在当前可见信息下恢复出的有限信息状态。

对手手牌未知时，不应将其视作完全未知，而可以对具体组件在手中的概率上界进行估计。若初始卡组中剩余卡牌数记作：

```text
n_rest = 30 - (n_deck - n_decktoken) - (n_play + n_discard) - n_harmony
```

手牌中剩余普通卡牌数记作：

```text
n_handrest = n_hand - n_handtoken
```

则一张特定剩余卡牌在对手手中的近似上手率可暂写为：

```text
P = 1 - (n_rest - n_handrest)^2 / ((n_rest - 2 * n_handrest) * n_rest)
```

这一表达尚未显式考虑以下因素：

- 基于手牌位置的精确追踪。
- 特殊卡牌在牌库中的固定位置。

本文采用以下记号：

- `s`：状态
- `a`：操作
- `A(s)`：状态 `s` 下的合法操作集
- `T(s, a)`：状态转移
- `V(s)` / `Q(s, a)`：价值

## 三、`def 1. 操作`

一次操作被定义为一个**带参数的具体操作实例**。当前先将以下对象统一视作同层级的操作：

- 调和
- 手牌打出
- 战斗切换
- 角色技能
- 回合结束

这样定义的原因，不是为了说明这些操作在战略意义上同质，而是因为在模拟器接口层，它们都表现为同层级的可执行动作；它们之间的战略差异，需要在价值函数或更高层分析中处理。

与此同时，本文保留“事件”这一层：

- 被动触发、召唤物触发、状态触发，视作事件，而非玩家主动操作。
- 死亡换人、强制切换等效果，当前更接近状态机中的强制结算；其是否应完全并入“操作”，仍需继续核对模拟器实现。

操作必须精确到实例层面：

- 同一张牌在不同目标上使用，是不同操作。
- 同一技能由不同角色施放，是不同操作。
- 同一动作采用不同支付方式，也是不同操作。
- “手牌打出”必须精确到具体卡牌，必要时还要精确到卡牌附属状态。
- “角色技能”必须细分到技能 id，必要时也包括装备赋予的特技。

快速行动切人与战斗行动切人必须显式区分。它们未必改变操作上界，但会改变轮次结构，从而影响后续价值。

## 四、`def 2. 合法操作`

合法操作集 `A(s)` 指状态 `s` 下，全部满足规则约束的具体可执行操作。这里的“合法”至少同时包含：

- 规则允许
- 资源足够
- 目标存在
- 阶段正确
- 时点正确
- 目标选择
- 支付方式

因此，合法操作不是一个抽象类别列表，而是一个随状态变化的具体实例集合。

一次操作执行后，状态发生变化：

```text
s' = T(s, a)
```

通常有：

```text
A(s') != A(s)
```

免费行动、减费、改骰、产骰等效果，都会直接改变合法操作集的大小与结构。

对手未知信息不会影响“合法性”本身，因为合法操作所需的信息都是公开的。未知信息影响的是后续价值判断，而不是 `A(s)` 的定义。

## 五、操作数边界、资源边界与搜索树深度

本文中的“每回合操作数”，暂指**单个玩家在一个回合内的总操作数**。它等于该玩家全部连续行动段中操作数的总和；若考虑整轮，则再把双方回合操作数相加。

当前可以先整理出几个稳定结论：

- 规则意义下的操作数下界应为 `0`。
- 玩家可以直接结束回合。
- 极端情况下，也可能出现由于冻结等原因导致几乎没有有效展开的状态。

另一方面，不能再把单回合操作数简单等同于“8 颗基础骰子能支持几次行动”。原因在于：

- 存在 `0` 费或变相免费行动。
- 存在产骰、返还骰、减费等效果。
- 操作数还受初始手牌、抽牌、生成牌、夺取手牌、手牌上限等因素约束。

因此，更稳妥的写法是将两类边界拆开：

- 操作数边界
- 资源消耗边界

原先“8 次战斗切换”的例子仍可保留，但只能作为基于基础规则的粗略上界说明，而不能视作完整上界。

至少截止 `V6.5`，技能最多消耗 `5` 颗骰子这一点仍然成立。

## 六、状态空间、操作序列空间与组合爆炸

在搜索复杂度问题上，应优先讨论状态空间，而不是直接从排列数出发。操作序列空间可以视为状态之间态射所构成对象的进一步组合；但对 AI 来说，更直接的难点是：

1. 每一步合法操作很多，所以分支因子很大。
2. 单回合可执行操作往往不止一步，所以搜索树很深。
3. 操作执行后还会引入新的资源、组件与局面变化，因此后续状态继续扩张。

除了过牌之外，下列因素也会使状态进一步扩张：

- 造骰
- 生成牌
- 召唤物生成
- 充能变化

若把每一步候选操作数粗略记为 `n`，则直接使用 `n!` 只能表达一个不够精确的直觉，因为：

- 它默认候选操作彼此不同。
- 实际上存在重复操作类别。
- 更准确的表达可能要借助多重集合排列，或者直接写成随深度变化的分支因子连乘。

因此，这一节目前更适合写成一个方向性结论：

> 七圣召唤的操作组合呈极快的组合爆炸增长，以致朴素穷举在通常意义下不可行。

## 七、展开轴稀疏与启发式搜索的必要性

即使不考虑隐藏信息，七圣召唤也已经因为高分支因子与较深搜索深度而难以直接穷举。更关键的是，在庞大的合法操作序列中，真正有实战价值的展开轴往往极其稀疏。

这里的“稀疏”，当前最适合先理解为：相对于全部合法操作序列而言，真正能够通向关键阈值、或者具有明显实战收益的路径，占比极低。

因此，启发式搜索的必要性主要来自：

- 分支因子过大
- 搜索深度过大
- 有效路径相对于全部路径极度稀疏

隐藏信息并不是这里的根本原因。它会提高建模难度，但不是搜索难以成立的第一推动力。

当前已有两个代表性例子：

- 林龙马构筑极度依赖圣遗物组件与费用链条的特定顺序。
- 吞星之鲸体系要求主动把调和组织成特定费用结构的组合。

这类卡组的共同点在于：表面上合法操作很多，但真正能进入有效展开的顺序极少。也正因此，低质量 AI 对局数据往往几乎全部来自“没有找到展开轴”的反例。

本文现阶段的目标，是说明**启发式是必要的**；至于具体搜索算法处于什么层级、采用什么形式，暂不在这一版强行确定。

## 八、价值目标：为什么不能直接最大化局部指标

大多数直观的局部目标，都不足以作为通用的一阶目标：

- 即时伤害对绝大多数非极限快攻卡组不适用。
- 本回合击倒概率对控制卡组甚至可能无法收敛，也未必构成局部最优。
- 资源优势对快攻卡组并不公平。
- “综合价值”如果不拆项，会过于模糊。

因此，目前更合理的整理方式是：

- 一级目标：整局胜率
- 二级代理目标：节奏、血量，以及后续可继续补充的中间量

也就是说，本文后面讨论的伤害收益、低血量风险等指标，更适合作为**胜率的代理变量**，而不是彼此孤立的最终目标。

至于是否要为不同 archetype 单独定义条件性价值函数，目前仍然偏难。现阶段更适合先保留“通用理论”的目标，再在后续承认不同卡组可能需要不同参数。

## 九、总评估函数的最小结构

当前更合适的写法，不是把所有价值压成一个统一的线性式子，而是先承认七圣召唤里的很多判断本身就是分层的。模型不会先问“总分是多少”，而是先问：

- 这个操作的即时收益是什么。
- 它为未来展开创造了什么。
- 它占用了什么关键资源或关键窗口。
- 它引入了什么风险。

因此，当前最可用的中间表达可以写成：

```text
Q_total(s, a) =
  G_now(s, a)
  - C_now(s, a)
  + G_plan(s, a)
  - C_plan(s, a)
  - R(s, a)
```

也可以写成更口语化的版本：

```text
Q_total(s, a) =
  （即时收益 - 即时机会成本）
  + （未来展开收益 - 展开机会成本）
  - 风险
```

这里有几个重要含义：

- 这不是说七圣召唤可以被简单加法完全刻画；它只是一个便于继续拆分的总框架。
- “机会成本”不作为独立大项，而是进入各局部收益项的对应反面。
- 不同 archetype 之间差异过大，因此未来更可能是在统一大框架下，只激活部分因子，或动态筛掉无关项，而不是要求所有卡组共享完全相同的局部结构。
- 七圣召唤更接近“分层 + 阈值 + 局部加和”的混合结构，而不是纯线性模型。很多量在达到阈值前几乎没有收益，一旦跨过阈值，局面价值就会跳变。

### 9.1 即时收益 `G_now(s, a)`

即时收益指的是：

> 执行操作 `a` 后，在当前行动窗口内已经兑现、或几乎不需要再额外投资关键资源就能兑现的价值。

当前可以先把即时收益拆成四类子项：

```text
G_now(s, a)
≈ D_now(s, a)
+ K_now(s, a)
+ M_now(s, a)
+ T_now(s, a)
```

其中：

- `D_now`：当前窗口内已经兑现的伤害收益。
- `K_now`：当前窗口内形成的击倒、斩杀线压制或角色功能坍缩。
- `M_now`：当前窗口内已经兑现的资源变化。
- `T_now`：当前窗口内已经成立的节奏变化。

#### 9.1.1 `D_now`：即时伤害收益

当前可以先归入：

- 直接伤害
- 当前行动内已经结算的反应伤害
- 当下已经触发的穿透、分段或后续触发伤害

这里的关键是：

- 伤害必须已经在当前窗口里变成既成事实，而不是只形成了潜力。

#### 9.1.2 `K_now`：即时击倒与功能压制收益

当前可以先归入：

- 立即形成的击倒
- 立即把对手压入强制响应区间
- 立即使对手当前出战角色失去本轮关键功能
- 立即改变对方可接受的换人、承伤或残局结构

这里单独拆出 `K_now` 的原因是：

- 在七圣召唤里，击倒不是普通伤害的线性累加，而是局面结构的跳变。

#### 9.1.3 `M_now`：即时资源收益

当前可以先归入：

- 已经拿到手且能立即使用的骰子、手牌或能量变现
- 当前行动内已经兑现的召唤物 / 支援物收益
- 当前窗口里已经落袋的资源差

这里要注意：

- 某个资源若只是为未来铺路，而没有在当前窗口兑现，更适合记到 `G_plan`。

#### 9.1.4 `T_now`：即时节奏收益

当前可以先归入：

- 直接交换先后手
- 当前窗口内直接迫使对手做出劣响应
- 立刻改变双方行动顺序与出手窗口
- 立刻形成站位优势或响应优势

这里的判断标准是：

- 该节奏变化是否已经在当前轮次内发生，而不是只提高未来的节奏潜力。

### 9.2 即时机会成本 `C_now(s, a)`

即时机会成本指的是：

> 为了得到当前操作的即时收益，当下已经付出的、且会立刻限制后续选择的代价。

当前可以先把即时机会成本拆成三类：

```text
C_now(s, a)
≈ R_now(s, a)
+ X_now(s, a)
+ P_now(s, a)
```

其中：

- `R_now`：当前窗口直接消耗掉的关键资源。
- `X_now`：当前窗口直接暴露出的结构性弱点。
- `P_now`：为了当前动作而放弃的其他即时高价值动作。

#### 9.2.1 `R_now`：即时资源代价

- 消耗关键骰子
- 消耗关键手牌
- 提前交出当前窗口里本可保留的能量、附着或位置优势

#### 9.2.2 `X_now`：即时暴露代价

- 把关键角色暴露在当前轮次的危险窗口中
- 把当前出战角色放到更差的位置结构中
- 让对手在当前响应面前更容易拿到局部优势

#### 9.2.3 `P_now`：即时路径放弃代价

- 为了当前收益而放弃同窗口内更高价值的即时动作
- 在同一轮次内提前锁死更优的即时顺序

### 9.3 未来展开收益 `G_plan(s, a)`

未来展开收益指的是：

> 该操作没有在当前窗口里把价值完全兑现，但它把局面推向了更容易产生高价值后续动作的状态。

当前可以先把未来展开收益拆成四类：

```text
G_plan(s, a)
≈ E_plan(s, a)
+ S_plan(s, a)
+ L_plan(s, a)
+ T_plan(s, a)
```

其中：

- `E_plan`：未来可转化资源的增长。
- `S_plan`：中间状态的建立与续存。
- `L_plan`：关键展开轴的解锁。
- `T_plan`：未来节奏空间的扩张。

#### 9.3.1 `E_plan`：未来资源兑现收益

当前可以先归入：

- 充能增长
- 尚未兑现但已建立的资源发动机
- 未来几步更容易获得的骰子、手牌或召唤物收益

#### 9.3.2 `S_plan`：中间状态收益

当前可以先归入：

- 为后续反应铺路的元素附着
- 召唤物 / 支援物的建立与续存
- 更优的轮转位置
- 某角色接近可兑现窗口的状态变化

这里的关键是：

- `S_plan` 处理的是“中间状态的价值”，也就是那些还没变成伤害与胜负、但已经显著改变后续可达性的量。

#### 9.3.3 `L_plan`：展开线解锁收益

当前可以先归入：

- 对后续关键展开轴的解锁
- 对组合技顺序要求的满足
- 对关键组件使用顺序的铺设

#### 9.3.4 `T_plan`：未来节奏收益

当前可以先归入：

- 对对手最优决策空间的限制
- 逼出换人
- 强制对手响应
- 使对手在未来轮次更容易掉入被动响应

也就是说，`T_plan` 不是现在已经拿到的节奏，而是未来更容易占据节奏主动的结构优势。

### 9.4 展开机会成本 `C_plan(s, a)`

展开机会成本指的是：

> 该操作虽然可能创造了某条展开线，但同时削弱、封锁或提前消耗了其他更优的未来路径。

当前可以先把展开机会成本拆成三类：

```text
C_plan(s, a)
≈ B_plan(s, a)
+ N_plan(s, a)
+ F_plan(s, a)
```

其中：

- `B_plan`：未来路径收窄。
- `N_plan`：卡组意图暴露后的对手适应空间上升。
- `F_plan`：未来展开对苛刻条件的依赖度上升。

#### 9.4.1 `B_plan`：未来路径收窄代价

- 提前交出组合技组件
- 打断原本更优的轮转顺序
- 让未来几步可行动作集变窄

#### 9.4.2 `N_plan`：对手适应代价

- 过早暴露卡组意图，使对手更容易做针对性应对
- 让对手更早识别出己方真正的胜利路径

#### 9.4.3 `F_plan`：未来脆弱性代价

- 让后续必须依赖更苛刻的抽牌、骰子或站位条件
- 让未来展开更容易被单点干扰打断

### 9.5 风险 `R(s, a)`

风险指的是：

> 该操作把己方局面推进到未来功能丧失概率更高、或一旦出错就更难挽回的状态的程度。

在工程评分层里，当前先把风险单列出来，而不急着完全压进别的项。当前可以先把风险拆成三类：

```text
R(s, a)
≈ R_role(s, a)
+ R_window(s, a)
+ R_state(s, a)
```

其中：

- `R_role`：关键角色功能坍缩风险。
- `R_window`：当前或下一轮兑现窗口被破坏的风险。
- `R_state`：局面整体分布滑向更差区域的风险。

#### 9.5.1 `R_role`：角色功能风险

当前可以先归入：

- 关键角色未来可兑现收益下降
- 关键角色完成当前职责的概率下降
- 角色由核心功能坍缩到战术功能或残余功能

#### 9.5.2 `R_window`：时间窗口风险

当前可以先归入：

- 己方站位暴露在更危险的响应面前
- 对手在下一轮或本轮后段形成更高质量反制的可能性上升
- 本轮职责窗口被压缩、打断或迫使延后

#### 9.5.3 `R_state`：局面分布风险

当前可以先归入：

- 某个操作把局面带入更差的未来状态分布
- 一旦对手抽到、做对或响应成功，己方局面将更难挽回
- 己方从“可修复局面”滑向“必须依赖高波动补救”的局面

风险的核心不是“会不会死”，而是：

- 这一步会不会让关键功能更容易坍缩。
- 这一步会不会让未来的容错空间显著下降。

### 9.6 归类原则：一个效果应该记到哪里

很多效果并不是天然只属于某一个项。为了避免重复计数，当前可以先用“主导兑现时间 + 主导作用方式”来归类。

#### 9.6.1 按主导兑现时间归类

- 如果价值已经在当前窗口兑现，优先记入 `G_now`。
- 如果价值要靠后续至少一步关键资源转换才能兑现，优先记入 `G_plan`。

例如：

- 上元素若立即触发反应并造成伤害，更接近 `G_now`。
- 上元素若主要是在为下一步反应铺路，更接近 `G_plan`。
- 充能通常更接近 `G_plan`，因为它通常还需要下一次资源兑现。

#### 9.6.2 按主导代价类型归类

- 如果代价主要体现在“现在少了一步更强动作”，优先记入 `C_now`。
- 如果代价主要体现在“未来展开线被削弱或封死”，优先记入 `C_plan`。

#### 9.6.3 风险优先处理功能坍缩

- 如果一个负面效应主要表现为关键角色更容易失去功能，优先记入 `R(s, a)`。
- 如果它主要只是让某条展开线变窄，而不直接提高功能坍缩概率，更接近 `C_plan(s, a)`。

因此，当前不是要求每个效果只能机械地放进一个桶里，而是要求：

- 每个效果只按“主导作用”计一次。
- 次级影响留在解释层，不重复进入评分。

### 9.7 哪些子项更适合近似量化，哪些更适合阈值判断

当前不应假定所有子项都适合同一种表示方式。更稳妥的做法是把它们分成三类：

- 适合近似量化的项
- 适合阈值判断的项
- 适合分段或混合处理的项

#### 9.7.1 适合近似量化的项

这类项通常具有较强的可计数性、可归一化性，或者至少能找到较稳定的 proxy：

- `D_now`
- `M_now`
- `R_now`
- `E_plan`
- `S_plan` 中可计数的部分
  - 例如召唤物剩余次数
  - 支援物剩余轮次
  - 可见附着与可见能量进度

这些项更适合先写成：

- 标量近似
- 归一化分数
- 与基础资源单位挂钩的 proxy

原因在于：

- 它们的兑现方式相对直接。
- 它们的量纲虽然不完全一致，但至少能在固定场景下稳定比较大小。

#### 9.7.2 更适合阈值判断的项

这类项的核心不是“多一点更好”，而是“是否跨过了关键门槛”：

- `K_now`
- `L_plan`
- `T_plan`
- `R_role`
- `F_plan` 中与组合技成立条件直接相关的部分

例如：

- 是否形成击倒
- 是否把对手压入必须响应区间
- 是否满足关键展开轴的先决条件
- 是否让某角色从“可执行核心功能”跌到“只能执行残余功能”

这些项如果硬做线性化，往往会丢掉最关键的信息。它们更适合先写成：

- 二值阈值
- 多档位阈值
- 条件成立/不成立的门控项

#### 9.7.3 更适合分段或混合处理的项

还有一批项既不是纯数值，也不是纯门槛，更适合做分段函数、区间打分或规则+数值混合：

- `T_now`
- `X_now`
- `B_plan`
- `N_plan`
- `R_window`
- `R_state`

这些项的共同点是：

- 它们通常会随局面变化而“突然重要起来”。
- 在低强度局面里可能几乎不重要。
- 一旦进入关键轮次、关键资源窗口或关键角色生死线，它们的权重会急剧上升。

因此，这类项更适合：

- 平时低权重
- 进入关键窗口后切换到高权重
- 或者直接按条件触发不同打分规则

#### 9.7.4 当前建议

如果后续要真的落到实现，当前最稳妥的顺序是：

1. 先把 `D_now`、`M_now`、`R_now`、`E_plan` 做成近似量化项
2. 把 `K_now`、`L_plan`、`R_role` 做成阈值项
3. 最后再处理 `T_now`、`T_plan`、`R_window`、`R_state` 这类混合项

这样做的原因是：前两类最容易先做出一个可运行的骨架，而第三类最容易把系统复杂度迅速拉高。

### 9.8 哪些是通用项，哪些是 deck-specific 项

当前也不应假定所有子项都需要 deck-specific。更合理的拆法是：

- 通用核心项
- 带参数的半通用项
- 明显 deck-specific 项

#### 9.8.1 通用核心项

这类项几乎对所有卡组都成立，因此最适合作为第一层公共框架：

- `D_now`
- `M_now`
- `R_now`
- `K_now` 的基础击倒部分
- `R_role` 的基础生存风险部分
- `R_window` 的基础响应窗口部分

这些项之所以通用，是因为它们对应的是七圣召唤几乎所有对局都共享的底层结构：

- 伤害
- 资源
- 击倒
- 生存
- 出手窗口

#### 9.8.2 带参数的半通用项

这类项的结构是通用的，但权重、阈值或解释方式需要随卡组变化：

- `T_now`
- `E_plan`
- `S_plan`
- `T_plan`
- `X_now`
- `R_state`

例如：

- 充能增长对快攻和控制的重要性不同
- 轮转位置对站场型卡组和后台反应型卡组的重要性不同
- 某个中间状态是否值得重视，取决于卡组真正的兑现路径

因此，这类项更适合：

- 保留统一结构
- 允许不同 archetype 使用不同参数、阈值或屏蔽规则

#### 9.8.3 明显 deck-specific 项

这类项很难脱离具体卡组、构筑和展开轴单独定义：

- `L_plan`
- `B_plan`
- `N_plan`
- `F_plan`
- `K_now` 中与“角色功能坍缩”直接相关的部分
- `R_role` 中与“核心功能是否 still relevant”直接相关的部分

原因很直接：

- 关键展开轴本来就是卡组相关的
- 更优路径与次优路径的区分本来就是卡组相关的
- 某角色失去功能到底意味着什么，也高度依赖构筑目标

因此，这类项更适合后置处理：

- 要么做 deck template
- 要么做 archetype-level 的规则注入
- 要么依赖数据驱动在更高层自动学习

#### 9.8.4 当前建议

如果目标是先做一个可实现的骨架，而不是一开始就追求“理论最全”，当前更稳妥的顺序是：

1. 先实现通用核心项
2. 再给半通用项加参数化
3. 最后再处理明显 deck-specific 的项

这样可以避免一开始就把系统绑定在某个具体卡组上，也能保留之后继续加深的空间。
## 十、进入总评估函数的变量

### 10.1 资源项

当前可以先视作资源项的包括：

- 血量
- 骰子（数量与颜色质量合并为一个骰子变量）
- 充能
- 召唤物剩余价值
- 支援物剩余价值
- 手牌

这里的“资源”不应只理解为静态数量，而应理解为后续能否转化为收益的能力。

### 10.2 节奏与位置结构

当前更适合单独放入节奏或位置结构中的包括：

- 当前出战角色
- 后台角色状态
- 行动权归属
- 轮次优势
- 反应风险或反应准备度

这里还需要一个术语说明：

> “未来伤害或风险的中间状态”，指的不是最终收益本身，而是那些还没有立刻兑现成伤害或风险、但会显著改变后续收益与风险的局面量。

例如：

- 当前出战角色是谁
- 后台是否处于可安全切上的状态
- 某角色是否已经有元素附着
- 某角色是否已经接近充满能量
- 某召唤物是否还能稳定触发一轮

这些量本身未必直接造成收益，但会强烈决定下一步的伤害、风险与节奏，因此应被视作中间状态。

### 10.3 机会成本

当前更适合把机会成本视作各局部收益项的负向对应，而不是单列独立大项。例如：

- 消耗关键骰子，对应即时机会成本。
- 交出关键手牌，对应展开机会成本。
- 暴露关键角色，对应风险增长或节奏损失。
- 放弃更优展开轴，对应未来展开收益下降。

## 十一、`def 3. 伤害收益`

“预期伤害”不能只由技能面板值决定。当前可以先把其不确定性来源整理为以下几类：

- 随机生成牌与抽牌带来的组件可得性差异
- 对手未知手牌导致的应对差异
- 对手策略差异
- 元素附着虽然公开，但后续反应能否稳定触发仍受双方策略影响

基础造成伤害的操作至少包括：

- 角色技能
- 召唤物触发
- 状态触发
- 卡牌直伤

反应伤害应并入同一个模型。穿透伤害、分段伤害则需要单独区分，因为它们对击倒节奏与后续收益的影响不同。

增伤来源当前可以先整理为：

- 武器
- 圣遗物
- 天赋
- 事件牌
- 角色状态 / 出战状态

由于部分增伤只作用于特定技能类型，因此技能必须带标签。一个当前可用的中间表达是：

```text
预期伤害
= 基础伤害
+ 条件性修正
+ 反应项
+ 后续触发项
```

此外，即使某个操作本身不直接造成伤害，只要它为后续反应、斩杀线或强制响应创造条件，它的收益仍应归入更广义的“伤害收益”分析中。

## 十二、非直伤收益的归类方式

非直伤收益目前不适合强行塞进单一类别里，更稳妥的做法是先分项建模，再在总评估函数中汇总。

当前可以先整理成以下结构：

### 12.1 可以并入广义伤害收益的项

- 上元素

这里不是说“上元素本身就是伤害”，而是说它的收益主要体现在后续反应所产生的伤害潜力，因此暂时并入更广义的伤害收益分析是合理的。

### 12.2 作为独立项处理的项

- 己方全队充能

充能不能只看当前出战角色，还要考虑类似 `白垩之术`（`332009`）这类会改变充能使用位置的牌，以及 `312014`、衍生物 `123031` 这类会让充能以非元素爆发方式变现的情况。因此，把充能独立建模是合理的。

### 12.3 并入节奏项的项

- 逼出换人
- 强制对手响应

“展开限制”可以视作节奏的一部分。许多看上去像控制效果的收益，最终更适合统一落到“改变对手最优决策空间”的节奏收益里。

### 12.4 与风险耦合较深的项

- 消耗对方骰子

资源差在七圣召唤里不一定值得单独最大化，它更像是在改变对手未来可执行动作的安全边界。因此，把它更多理解为“对手风险上升”而不是“我方纯资源领先”，是成立的。

## 十三、`theorem 3` 的方向：理论价值层与工程评分层

真正需要的不是“本次技能打多少伤害”，而是“执行这一操作后，局面价值如何变化”。当前更适合把这一节拆成两个层级：

- 理论价值层：`U(s_terminal)`、`V(s)`、`Q(s, a)`
- 工程评分层：`Q_total(s, a)`

这样做的好处是：一方面保留了理论上更干净的状态价值与动作价值概念；另一方面，也允许在工程实现中继续使用更可解释、可拆分的局部评分项，而不必过早把所有内容都压成一个不可读的单一公式。

### 13.1 终局收益 `U(s_terminal)`

当前最明确的锚点是：

- 终局收益 `U(s_terminal)` 可以先定义为胜负二值。

这给后续递归提供了一个边界条件。若之后需要处理控制卡组内战等场景，再在此基础上增补平局处理即可。

### 13.2 `V(s)` 与 `Q(s, a)`

如果强调策略依赖性，更严格的写法应为 `V_π(s)` 与 `Q_π(s, a)`；若暂时不显式写策略下标，也可以沿用 `V(s)` 与 `Q(s, a)` 的简写。

当前更适合把它们理解为：

- `V_π(s)`：某个策略 `π` 下，从状态 `s` 出发所能获得的期望价值。
- `Q_π(s, a)`：在状态 `s` 下先执行操作 `a`，再沿策略 `π` 继续对局时的期望价值。

两者的关系可以先写成：

```text
V_π(s) = E_{a ~ π(.|s)} [Q_π(s, a)]
```

如果未来要讨论最优策略，再额外引入 `V*(s)` 与 `Q*(s, a)` 即可；现阶段不必写死。

### 13.3 `Q(s, a)` 的概念性分解

当前更适合把 `Q_π(s, a)` 理解为两部分：

- 执行操作 `a` 所造成的即时局部影响。
- 进入新状态 `s' = T(s, a)` 之后，沿策略 `π` 继续对局所带来的未来状态价值。

也就是说，`Q_π(s, a)` 不是纯即时数，也不是只和伤害有关，而是一个“当前操作对后续局面的总影响”的期望表示。

这也解释了为什么仅靠即时伤害无法替代真正的动作价值：很多操作的主要收益不在当前数值，而在于它改变了后续可展开的空间。

### 13.4 `Q_total(s, a)` 作为工程评分层

当前更稳妥的理解是：

> `Q_total(s, a)` 不是一个与 `Q(s, a)` 平行的新理论对象，而是工程上用于近似、展开和解释 `Q(s, a)` 的评分写法。

也就是说：

- `Q(s, a)` 更接近理论上的动作价值。
- `Q_total(s, a)` 更接近实现时可分解、可调权、可解释的评分结构。

因此，当前最可用的工程表达可以写成：

```text
Q_total(s, a) =
  （即时收益 - 即时机会成本）
  + （未来展开收益 - 展开机会成本）
  - 风险
```

这里的关键不是它已经足够精确，而是它已经明确了：

- 机会成本不单列为完全独立的大项，而是进入各局部收益项的对应反面。
- 风险暂时保持显式列出，不急着完全压进其他项中。
- 这个评分结构服务于对 `Q(s, a)` 的近似，而不是取代理论层本身。

### 13.5 折扣系数

当前最适合保留的主解释是：

- 折扣系数代表时间偏好。

这比把它同时解释成时间偏好、不确定性和搜索截断的混合量更干净。后两者如果以后确实要处理，最好另找变量，不要都塞进同一个折扣系数里。

### 13.6 当前仍保留的开放点

下面这些点仍未收束：

- `Q_total(s, a)` 的子项是否还需要继续细分到更具体的 deck-specific 因子。`r`n- 理论层是否始终显式写成 `V_π(s)` / `Q_π(s, a)`，还是保留简写。
- `V(s)` 是否最终要写成逼近终局收益期望的明确形式。

## 十四、`theorem 4` 的方向：从剩余血量到功能丧失概率

这里的“风险”，已经明显不应再理解为“剩余血量越低越危险”的线性判断。更准确的说法应该是：

> 风险表示角色在未来若干行动内失去其战术功能的概率与代价。

这里的对象首先是单个角色，而且不局限于出战角色，因为部分效果可以命中后台。

### 14.1 已经较稳定的结论

- 风险更接近“未来无法履行职责的风险”，而不是单纯的“被击倒风险”。
- 计数尺度更适合按双方行动计，而不只是按完整回合计。
- 一个 `1` 血后台辅助与一个 `1` 血主输出，其风险显然不同。
- 护盾、治疗、禁疗、减伤、冻结、石化、眩晕、强制切换等效果，都应进入风险模型。

### 14.2 风险来源

对方伤害序列的来源，目前可以先整理成四类：

- 历史统计
- 搜索模拟
- 套牌先验
- 最坏情况近似

### 14.3 功能的层级性

当前更适合把“功能”理解为：

> 某个角色在当前局面与时间窗口下，仍然值得被保留、调用或围绕其组织资源的理由。

这样一来，“失去功能”就不再等同于“被击倒”，而是指：

> 在当前要求的时间窗口内，角色已经无法可靠地完成其当前层级上最重要的任务。

为了让这个概念更可用，可以先把角色功能拆成三层：

- 核心功能：该角色在卡组胜利路径中的长期任务。
- 战术功能：该角色在当前或下一轮中可兑现的局内任务。
- 残余功能：当核心功能与战术功能都难以成立时，角色仍然保留的最低限度用途。

#### 14.3.1 核心功能

核心功能由卡组、配队、构筑共同决定，回答的是：

- 这个角色为什么会被放进这套牌里？
- 这套牌的胜利路径里，理论上希望它承担什么职责？

例如：

- 站场输出角色：提供主要输出窗口。
- 后台挂元素角色：稳定提供元素附着或反应触发条件。
- 治疗 / 保护角色：维持关键角色的生存阈值。
- 资源发动机角色：制造骰子、充能或额外手牌等中间资源。

当这些长期职责已经无法兑现时，可以说该角色的核心功能已经丧失。

#### 14.3.2 战术功能

战术功能回答的是：

- 在当前这一个轮次或接下来极短的时间窗口内，这个角色还能具体做什么？

例如：

- 还能否安全站场并完成一次有效输出。
- 还能否在需要时切上来挂元素、治疗、保护或吃伤害。
- 还能否依靠已存在的能量、附着、装备或站位，在本轮把资源兑现成收益。

很多时候，角色的核心功能还在，但战术功能已经暂时丧失；或者核心功能已经基本失败，但短期战术功能仍然存在。风险模型真正需要盯住的，往往是这一层。

#### 14.3.3 残余功能

残余功能是当角色已经难以完成主要任务时，仍然保留的最低限度用途。当前至少包括：

- 承伤
- 拖动数
- 吸收对手关键行动
- 配合残局类效果或死亡触发类效果

因此，一个角色即使已经失去核心功能，也未必完全失去价值；只是它的价值层级下降到了残余功能。

#### 14.3.4 “失去功能”的判定

综合来看，“失去功能”更适合被理解为：

- 失去核心功能：已无法支撑其在卡组胜利路径中的主要职责。
- 失去战术功能：在当前轮次或最近的兑现窗口内，无法可靠地产生预期收益。
- 失去残余功能：连承伤、拖动数或配合残局的最低限度用途也不存在。

这一定义的好处是：角色价值不再是单次断裂，而是分层坍缩。风险不只是“会不会死”，而是“会先失去哪一层功能”。

### 14.4 风险的时间尺度

风险最低应以轮次计，而不是以单一步行动计。原因在于：组合技卡组能在一个轮次中打出大量快速行动，因此单步时间尺度太细，不能稳定反映风险。

当前更可用的拆法是：

- 短期风险：下一次行动的风险。
- 中期风险：完成本轮职责之前的风险。

并且这两者不是简单包含关系。

### 14.5 风险在整体框架中的位置

这一部分现在可以先明确成一条原则：

> 理论上，风险并入未来价值；工程上，风险暂时单列。

这句话的含义是：

#### 14.5.1 理论层

在理论价值层里，并不需要把风险当成一个与价值并列的神秘对象。只要未来价值 `V(s)` 足够完整，风险自然表现为：

- 某角色未来可兑现收益下降。
- 某角色完成当前职责的概率下降。
- 某操作把局面带入更差的未来状态分布。

因此，从理论上说，风险最终可以被视作未来价值下降的一种表现形式。

#### 14.5.2 工程层

但在工程评分层里，当前更稳妥的选择仍然是：

- 风险保持单独一栏，供策略层使用。

这样做有几个好处：

- 保留结构信息，不会过早把不同类型的危险压扁成一个数。
- 更方便做 deck-specific 的阈值判断。
- 更容易和“即时收益”“未来展开收益”区分，避免重复计数。
- 更利于人工复盘和后续解释模型决策。

#### 14.5.3 哪些风险可以局部并入其他项

虽然风险整体先单列，但某些局部风险已经可以部分并入其他项：

- 暴露关键角色：可以表现为即时机会成本或节奏损失。
- 消耗对方骰子：更接近改变对手安全边界，因此可以通过风险上升来体现。
- 反应准备度：既是未来伤害的中间状态，也是短期风险来源。

也就是说，当前不是“完全单列”或“完全并入”二选一，而是：

- 总体上单列。
- 局部上允许有归属。

#### 14.5.4 当前结论

因此，当前最稳妥的写法是：

- 理论层：风险通过未来价值下降体现。
- 工程层：风险作为单独项显式列出。
- 更细的并入规则，等 `Q_total(s, a)` 的子项定义更清楚后再继续收紧。

## 十五、当前仍未收束的问题

下面这些点仍然没有稳定下来，因此暂时不建议写死：

- 死亡换人与强制切换究竟应归入操作还是强制结算。
- 元素附着在“状态空间扩张”一节中的准确地位。
- 总评估函数各层之间究竟怎样正式连接。
- `Q_total(s, a)` 的子项、阈值与筛选规则如何正式定义。
- `V(s)` 与终局收益之间的最终写法。
- “功能”这一概念的层级定义，仍然只有方向感，还没有形式化表达。
- 例子与验证部分暂未并入主文档。

## 十六、下一步

接下来更稳妥的推进顺序不是立刻补公式，而是：

1. 先把这套主线固定下来。
2. 再单独整理 `Q_total(s, a)` 的正式结构与各子项定义。
3. 最后用具体牌组和具体局面补例子，反过来检验这套框架是否真的能解释对局。






## 十七、RL 视角下的最小实现骨架

如果目标是把上面的理论框架推进到“可训练、可评测、可迭代”的 RL 系统，那么当前最小实现不应一开始就追求完整处理隐藏信息、完整处理 deck-specific 价值函数，也不应试图把 `Q_total(s, a)` 的全部子项一次性写成奖励函数。更稳妥的路径是：

> 先构造一个能跑通 `状态 -> 合法动作集 -> 动作评分 / 采样 -> 状态转移 -> 终局回传` 的最小闭环，再逐步把理论结构灌进去。

### 17.1 observation：状态该怎样进入策略模型

RL 里的 observation 不应只是“当前局面截图”，而应是：

- 当前状态 `s` 的机器可读表示。
- 当前合法操作集 `A(s)` 的上下文。
- 少量已经验证有用的中间特征。

当前至少可以拆成四层：

#### 17.1.1 原始状态层

这层尽量忠实对应前文的 `def 0. 状态`，至少包括：

- 回合数、阶段、行动权归属。
- 双方出战角色、后台角色、血量、能量、附着、装备、状态、存活情况。
- 召唤物、支援、战斗状态。
- 我方手牌、骰子及其质量。
- 对方公开可见信息。

#### 17.1.2 合法动作上下文层

由于七圣召唤的动作空间是动态变化的，因此 observation 不应只看状态，还应同时看到：

- 当前 `A(s)` 的大小。
- 当前候选动作的类型分布。
- 当前候选动作各自的费用、目标、快慢行动属性、技能类型等。

也就是说，后续实现里更自然的对象不是“固定大动作空间”，而是：

> 对当前合法候选列表做打分或采样。

#### 17.1.3 中间特征层

这层就是理论框架和实现之间的桥。当前最值得先做成特征的，不是所有概念，而是那些较稳定、较通用的项，例如：

- 可造成的直接伤害或斩杀线接近度。
- 骰子与能量资源强度。
- 基本反应准备度。
- 关键角色当前功能层级是否完整。
- 本轮剩余兑现窗口是否仍在。

这些特征本质上是对 `G_now`、`E_plan`、`R_role`、`R_window` 等项的简化投影。

#### 17.1.4 隐藏信息层

七圣召唤不是完全信息博弈，因此 observation 迟早要处理：

- 对方手牌未知。
- 对方牌库剩余未知。
- 某些行动意图与保留资源未知。

但当前最小实现不必一步到位。更稳妥的起点是同时接受两套 observation 视角：

- `obs_debug_full`：调试或上界分析用，允许读取引擎内部全状态。
- `obs_policy_public`：真正策略训练主线使用，只包含公开信息、我方私有信息与少量对手先验统计。

前者帮助验证训练链路和特征定义；后者才更接近真实策略问题。

### 17.2 action：动作应如何定义给策略头

前文的 `def 1 / def 2` 已经给了动作语义层的定义。到了 RL 里，更需要解决的是“动作怎样编码”。

当前更稳妥的做法是：

- 把动作单位定义成 `A(s)` 中的一个具体合法动作实例。

这意味着一个动作应至少包含：

- 操作类型。
- 具体对象或来源，如哪张牌、哪个技能、哪次切换。
- 目标选择。
- 支付方式选择。
- 如果当前 pending method 不同，还应包含当前请求类型。

因此，工程实现上更适合采用：

- `pending_method + candidate_index`

或与之等价的“对合法候选列表逐项打分”的接口，而不应优先尝试：

- 把全游戏所有动作硬压进一个固定大离散空间。

原因很直接：

- 合法动作集合本来就是状态相关的。
- 同一技能在不同支付与目标选择下，本来就是不同动作实例。
- 使用合法候选列表天然带 action mask。

### 17.3 reward：哪些东西适合进入奖励

当前理论层已经有：

- `U(s_terminal)`：终局收益锚点。
- `V(s)`：状态价值。
- `Q(s, a)`：动作价值。

因此 RL 奖励最稳妥的写法应先明确一条主原则：

> 终局奖励是锚，dense reward 只是辅助，不应反客为主。

当前更稳妥的奖励设计可以拆成两层：

#### 17.3.1 终局奖励

最小实现先使用：

- 胜利：`+1`
- 失败：`-1`
- 平局或异常终局：`0` 或单独约定

这对应前文的 `U(s_terminal)`。

#### 17.3.2 稠密 shaping 项

在此基础上，可以谨慎加入少量 dense proxy，但不宜把整个 `Q_total(s, a)` 原样当 reward。当前更适合作为 shaping 的，主要是：

- 生命值净变动或有效伤害。
- 击倒事件。
- 骰子、能量、手牌等基础资源净变化。
- 已达成的关键中间状态，如稳定反应准备、爆发线开启。
- 显著的功能风险变化，如关键角色从“战术功能完整”降到“仅残余功能”。

这些项加入时应满足四条约束：

- 终局奖励仍然占主导。
- shaping 项尺度较小，最好截断或归一化。
- 不对同一事件在多个槽位重复发奖。
- 明显 deck-specific 的高层概念，起步阶段不直接进入 dense reward。

也就是说，`Q_total(s, a)` 当前更适合作为：

- 奖励设计的候选池。
- 辅助监督目标。
- 解释与复盘框架。

而不是直接充当最终 reward 本身。

### 17.4 return：终局回传与价值学习

有了 reward 之后，return 才能接回前文的理论层。

当前最自然的关系是：

- 终局收益 `U(s_terminal)` 提供训练锚点。
- value head 逼近 `V(s)`。
- policy 或 candidate scorer 逼近 `Q(s, a)` 的相对优先级，或者逼近 advantage 类对象。

在这个结构里，`Q_total(s, a)` 的位置应写得更保守一些：

- 它不是 RL 理论中的真值。
- 它更接近工程上的近似展开、warm start 评分器或辅助标签。

因此，当前框架里最稳妥的连接方式是：

- 理论层：`U -> V -> Q`
- 工程层：`Q_total` 用来帮助构造特征、辅助监督、候选排序与决策解释

### 17.5 当前更推荐的最小训练路径

如果目标不是“先把公式写得很漂亮”，而是“尽快做出一个能跑的 baseline”，那么当前更推荐的路径是：

1. 先复用已有引擎和合法动作接口，固定 `状态 -> 合法候选列表 -> 执行动作 -> 新状态` 的闭环。
2. 用 `branch-eval / combat-window / replay / self-play` 数据先做离线 warm start。
3. 先训练一个对合法候选动作列表进行排序或打分的模型，而不是一步到位训练完整端到端策略。
4. 再引入终局奖励主导、少量 dense shaping 辅助的 self-play 微调。
5. 最后才处理更强的不完全信息建模与 deck-specific 扩展。

这个顺序的好处是：

- 可以先验证 observation 与 action contract 是否稳定。
- 可以先验证 `Q_total` 子项到底哪些真的有用。
- 可以避免一开始就把问题扩大成“全功能强博弈 RL”。

### 17.6 现有工程基础与缺口

从当前本地工程状态看，并不是一切都要从零开始。至少已经能看到几块直接相关的基础：

- `packages/mcp` 已经有 `GameStateSerializer`、`get_game_state`、`get_available_commands`、`choose_action` 等接口。
- `packages/gi-ml` 已经把 `branch-eval`、`combat-window`、`self-play`、`replay` 明确列为训练数据入口。
- `packages/gi-ml` 已经存在 `concept model train`、`ranker train`、runtime policy 等训练与运行时骨架。

这意味着当前距离“可实现 RL”真正缺的，不再主要是：

- 模拟器有没有。
- 合法动作能不能枚举。
- 数据入口是否完全不存在。

真正还缺的是下面这些更靠中间层的东西：

- 一套稳定的 observation contract。
- 一套把合法候选动作喂给模型的 action encoding contract。
- 一套克制且不自欺的 reward / shaping 设计。
- 一条在线 self-play 更新链路。
- 一套面向 deck archetype 与隐藏信息的后续扩展接口。

### 17.7 现在距离“可实现的 RL”还差多少

如果这里说的“可实现”是指：

- 能跑通训练闭环。
- 能在合法动作上做出选择。
- 能和若干 baseline 做稳定比较。

那么当前距离并不算特别远，更多是：

> 还差一轮实现规范化，而不是还差一整套新理论。

更具体地说，当前大致处在这样一个阶段：

- 理论主线已经足够支撑特征与奖励设计。
- 工程上已经能看到状态、合法动作、训练数据与部分 runtime 骨架。
- 但 observation、action、reward、return 四者之间还没有被写成统一契约。

因此，当前离第一个可跑的 RL baseline，主要还差五层：

- 观测编码层：把 `def 0` 与中间特征写成机器输入。
- 候选动作编码层：把 `A(s)` 稳定映射成模型可评分的列表。
- 奖励设计层：决定哪些项进入 shaping，哪些只留在终局回传。
- 训练闭环层：把 self-play、更新、评测串起来。
- 泛化边界层：决定先做 perfect-information proxy、public-information policy，还是两者并行。

如果这些层补齐，那么就已经可以开始训练一个“未必很强，但结构上正确”的 RL baseline。真正更远的部分，反而是：

- 把它做成稳定强策略。
- 处理高质量隐藏信息推断。
- 处理强 deck-specific 价值结构。
- 做跨卡组、跨环境版本的鲁棒泛化。

也就是说：

- 从现在到“能开训”，距离已经不大。
- 从现在到“强而稳的通用 RL agent”，距离仍然很大。

### 17.8 关于 observation / action 的当前实现参照

在实现层面，前两层目前可以直接参考 `genius-invokation/packages/mcp` 里的相关接口：

- `get_game_state`
- `get_screen_state`
- `get_available_commands`
- `choose_action`
- `get_character_info`
- `get_card_info`

它们至少已经提供了两件重要东西：

- 一套可直接读取的状态暴露接口。
- 一套与 pending RPC 对齐的合法动作入口。

但这套接口当前更接近“可交互策略工具”，还不完全等于“可直接喂给 RL 的 observation / candidate contract”。因此当前更合理的态度是：

- observation 层可把 `get_game_state` / `get_screen_state` 作为原始输入参照。
- action 层可把 `get_available_commands` + `choose_action(action_index)` 作为合法候选参照。
- 真正训练用的输入与候选编码，仍需要在其上再做一层更细的结构化整理。

尤其 observation 这一侧，`screen_state` 目前更像轻量交互视图，粒度很可能不够细；后续更可行的方向仍然是：

- 以 `get_game_state` 暴露的完整状态为底。
- 再额外抽取更贴近 `G_now / G_plan / R` 的中间特征。

换句话说，前两层当前不必从零构造，但也不能直接把 MCP 工具输出原样当作最终训练契约。

### 17.9 reward 设计层：当前最需要继续回答的问题

这一层真正要解决的，不是“奖励能不能写得更丰富”，而是：

> 什么奖励既能推动学习，又不会系统性地把策略带歪。

当前更适合按下面的顺序继续回答。

#### 17.9.1 终局奖励的定义

- 终局奖励是否固定为胜 `+1`、负 `-1`、平 `0`？是。
- 是否需要把投降、异常中断、非法终止单独归类？投降视作负，异常中断和非法终止不进入样本池。
- 终局奖励是否需要按先后手、回合数、剩余角色数再做修正？不需要
- 第一版是否坚持最简单的二值终局奖励，不引入额外胜法加成？是

#### 17.9.2 dense shaping 的边界

- 第一版是否只允许少量 shaping，而不把 `Q_total(s, a)` 整体奖励化
- 哪些项可以进入 shaping 白名单/黑名单，在后续完成训练闭环时再具体列出并筛选。
- 要把 shaping 分成通用项与 deck-specific 项，但第一版先只开通用项；deck-specific 项在后续迭代优化时再进入主训练线

#### 17.9.3 奖励事件的最小单位

- reward 是按单步 action 发放
- 快速行动链中的多个动作，逐步发 reward
- 死亡换人、强制切换、被动触发这些非主动事件，不单独触发奖励
- 同一个动作导致多段收益时，奖励是拆开发

#### 17.9.4 哪些项适合直接做 shaping

- 有效伤害进入 shaping，而不是原始伤害
- 击倒单独发奖
- 资源净变化里，骰子、手牌、能量要拆开算
- 反应准备度值得做成中间 shaping
- “爆发线开启”“稳定展开点形成”是否已经足够稳定，可以奖励
- 关键角色从“核心/战术功能完整”跌到“仅残余功能”，不作为风险惩罚事件

#### 17.9.5 哪些项暂时不适合直接做 shaping

- `L_plan` 这种高度 deck-specific 的展开线收益，第一版不禁止直接发奖
- `N_plan` 这种对手适应代价，先只做分析项不做 reward
- 高层节奏概念是否太依赖解释口径，暂时不奖励
- 风险项是否先只选极少数可稳定识别的事件，而不整体奖励化

#### 17.9.6 奖励尺度与归一化

- 各 shaping 项的绝对尺度如何与终局奖励保持从属关系？根据“功能层级”的概念以及操作序列的长度对shaping项的尺度进行分层赋值
- 是否要为所有 dense reward 做截断？是
- 是否要按回合长度、行动数、对局长度做归一化？不对回合长度做归一化，对行动数和对局长度做归一化。
- 是否要区分一次性事件奖励与持续性状态奖励？是
- 若同一回合能连续打出高频小收益动作，如何避免模型偏好“刷分”而不是求胜？“刷分”行为容易透支资源导致手牌或其他资源运转崩溃，是否可以在操作后进行修正？

#### 17.9.7 重复计数与归属冲突

- 一次击倒如果已经通过生命值变化体现，是否还单独给击倒奖？是
- 反应准备度既进入未来收益又进入风险变化时，如何避免双计？取和为1的系数进行分配
- 资源消耗既是成本又可能通向更大收益时，奖励该记在哪里？记在最终收益上
- 某动作同时带来立即伤害与展开解锁时，两部分是否分开发奖？是
- 同一事件在 `G_now / G_plan / R` 多个视角下都重要时，reward 只取哪个主导归属？不同卡组对G_now和G_plan倾向性不同，优先取G_plan

#### 17.9.8 reward 与理论层的关系

- reward 想逼近的是 `Q_total` 的局部 proxy
- dense shaping 是训练信号，同时也作为解释指标
- 需要把部分 `Q_total` 子项改写成辅助监督标签，而不是 reward
- 明确区分“环境奖励”和“分析评分”

#### 17.9.9 reward 的验证问题

- 如何判断当前 shaping 是否在帮助学习，而不是诱导 reward hacking？A/B对照+少量人工检查
- 是否需要专门构造反例局面，测试模型会不会为了资源分而放弃胜势？不需要，几乎都是反例局面
- 是否需要比较“只用终局奖励”和“加入少量 shaping”两条线？需要
- 评估时分两层看：shaping 设计先看学习速度提升，模型验收仍看最终胜率提升

### 17.10 训练闭环层：当前最需要继续回答的问题

这一层要解决的是：

> 前三层定义完之后，数据、更新、对手、评测到底怎样连成一个可持续迭代的系统。

#### 17.10.1 第一版训练路径

- 第一版是先离线 warm start，再 online self-play
- warm start 阶段采用行为克隆 / 排序学习，对策略头与价值头做多头联训
- candidate ranker 作为离线阶段的核心目标，value head 不再单独滞后训练，而是在统一框架下与 policy 一起优化
- 第一个 baseline 是规则策略、启发式策略

#### 17.10.2 数据来源如何分工

- `branch-eval`、`combat-window`、`replay`、`self-play` 各自承担什么角色？
  - branch-eval：最适合教“同一个局面下，几个候选动作谁更优”。
  - combat-window：最适合教“短窗口里的展开、爆发、节奏转换”。
  - replay：最适合教“真实轨迹长什么样、最后输赢怎样”。
  - self-play：最适合让训练分布逐渐靠近当前策略会遇到的真实局面。
- 先只用高质量 `branch-eval` / `combat-window` 做 warm start
- `self-play` 数据进入训练前需要筛选、重加权或去偏

#### 17.10.3 训练样本单位

- 一个训练样本是一个完整 decision point
- 候选动作学习时，是 pairwise、listwise，还是 pointwise？
- value 学习是按轨迹回传
- 需要同时保留局部窗口样本与完整对局样本

#### 17.10.4 模型目标与阶段拆分

- policy head 的目标是选动作、排候选
- value head 与 policy 联训
- concept/ranker 先独立训练再蒸馏到 RL 模型
- 第一版明确分成“离线排序器 -> 在线策略微调”两阶段

#### 17.10.5 self-play 的组织方式

- 对手池是镜像自博弈，混入旧 checkpoint
- 保留固定 baseline 对手，防止策略退化成互刷
- 对手采样比例如何设定？镜像40%，历史ckpt40%，baseline20%
- 不需要 curriculum（例如先镜像、后跨 deck、再跨 matchup）
- 需要专门的“难例池”或“高 regret 池”

#### 17.10.6 更新节奏与数据新鲜度

- 是边打边学，还是分轮生成数据再统一更新？边打边学
- replay buffer 保留多久的数据？全局
- 新旧数据比例如何平衡？7:3
- 若环境版本、卡池、reward 定义变化，旧数据是否还可复用？检查双方卡组是否有相关削弱卡牌，有则不可复用
- 多久评测一次、多大改进才接受新 checkpoint？
  - 相同对局的胜率上升2%对当前 best 模型总胜率 >= 54%（建议区间 53% 到 55%）
  - 对固定 baseline 不得明显退化（例如任一关键 baseline 胜率下降不超过 2%）
  - 在固定 matchup 回归集上无显著下滑（例如总胜率不下降超过 1%）

#### 17.10.7 评测协议

- 第一版最核心的评测指标是胜率
- 按 matchup 分层看表现
- 固定随机种子与固定对手池做回归测试
- 单独评测“短期强度”和“长期稳定性”
- 需要把“能解释为什么选这个动作”作为辅助评测标准

#### 17.10.8 失败诊断

- 若胜率不升，优先怀疑reward。regret 作为诊断指标，不作为第一验收指标。
- 需要记录每个 decision point 的候选列表、模型评分、最终选择与终局结果
- 构建一套“复盘样本集”，固定检查典型错例
- 要区分“学不会”和“学错了”这两类失败

#### 17.10.9 工程接口问题

- 当前训练 loop 是直接挂引擎、挂 mcp，还是先导出离线数据格式？第一版采用“双轨”：在线训练直接挂引擎；同时强制导出统一离线数据用于复现与回放分析。
- observation / action contract 单独版本化
- reward 配置独立于模型配置
- 先定义统一日志 schema，避免后面回放困难。模拟器支持记录对局，导出对局记录即可。把模型版本、环境版本、卡池版本、reward 版本、contract 版本全部写入每条对局记录。

### 17.11 泛化边界层：当前最需要继续回答的问题

这一层要解决的是：

> 第一版到底打算解决多大的问题，哪些难题先故意不碰。

这不是附属问题，而是对前四层的总约束。

#### 17.11.1 先做哪一类环境

- 第一版先锁死至少3个 archetype各一套（快攻、中速、控制），再逐步扩展
- 覆盖 mulligan / reroll / choose active
- 先在固定版本、固定牌池下做，不考虑环境变动

#### 17.11.2 信息边界

- 第一版策略允许读取完整引擎状态，作为 debug / 上界代理
- 真正训练主线只允许 public information + self private information
- 对手未知手牌第一版是统计期望
- 同时维护 `debug_full` 与 `policy_public` 两套实验线

#### 17.11.3 套牌与角色泛化边界

- 第一版只针对覆盖多个archetype的三套卡组
- deck-specific 价值项不进入第一版 warm start 与初始 RL 主线，而是在开始迭代优化时进入主训练线
- 先做“每套牌每一个对局一个专用策略”，再追求共享模型

#### 17.11.4 动作泛化边界

- 第一版要求系统层统一 contract 并覆盖所有合法动作类型
- 学习模型允许先只覆盖最常见动作，再对罕见动作退回规则策略
- 学习层可以采用“主头 + 回退头”的结构；边界动作与稀有 pending method 在统一 contract 下先由回退头或规则策略承接
- 元素调和、特殊选牌、死亡换人等动作在系统层仍保留统一编码

#### 17.11.5 目标泛化边界

- 第一版追求的是“学会合法且不太差”
- 先优化局部决策质量
- 是否要求模型在未见 matchup 上也稳定
- 把“可解释性”作为第一版硬要求

#### 17.11.6 版本与分布漂移

- 卡牌版本更新后，旧 observation / action / reward contract 应该都能复用
- 需要把版本号写进训练样本与评测协议
- 环境变化时重训，部分平衡性调整会导致展开路线剧变。
- 明确区分“规则泛化”和“元环境泛化”

#### 17.11.7 何时算第一版完成

- 第一版的最小完成标准是什么稳定跑通训练闭环，在一组固定 matchup 上成功
- 其他高阶目标明确列为第二阶段，而不在第一版验收范围内。

### 17.12 当前更建议的作答顺序

如果接下来要继续补文档，当前更建议的顺序不是同时回答全部问题，而是：

1. 先回答 `17.11`，也就是第一版边界到底画到哪里。
2. 再回答 `17.9`，确定奖励允许奖励什么、不允许奖励什么。
3. 最后回答 `17.10`，把训练闭环接起来。

原因很简单：

- 边界不定，reward 就会越来越散。
- reward 不定，训练闭环就只能写空流程。
- 先把这三层按顺序定下来，前两层 observation / action 的精细化反而更容易收束。

## 十八、结构改进方案（综合引导问答后更新）

> 基于 `missing-modules-guiding-questions.md` 全部回答、`framework-critical-gaps.md` 回答审查、及 gi-agent / gi-ml 现有代码分析后的综合更新。
> 取代此前对话中给出的 P0-P3 初版路线。

### 18.1 核心发现：三层决策的依赖链

D4 回答揭示了当前 AI 最根本的结构瓶颈：

> Game-level 缺失 → Turn-level 无锚 → Step-level 盲选

具体而言：

- 人类玩家的 Game-level 和 Turn-level 几乎不出错，胜负差距主要在 Step-level。
- 但 AI **三层全弱**——不是某一层弱，而是缺少 Game-level 策略目标后，后两层无法正常生成。
- 用户希望 Game-level 由 AI 自主发现，但承认可行性较低。

**结论**：第一版必须提供 Game-level 先验（至少是 archetype 级别的策略模板），而不是指望纯搜索或纯 RL 从零发现。

### 18.2 来自引导问答的关键约束

以下结论直接影响改进方案的技术选择：

| 来源 | 结论 | 对AI方案的影响 |
|------|------|-------------|
| **B1-B3** | 骰子价值完全上下文相关，万能骰 ≠ 恒定最优 | 骰子评估必须是状态条件函数，不能用静态权重 |
| **A3** | 挂元素总是收益更高，但面对自挂角色例外 | 反应收益模型需要条件分支，不能一刀切 |
| **A4** | 反应链是有意识设计的，AI 搜索很难找到 | 反应链需要先验模板或专门的搜索引导 |
| **C1** | 阶段转换没有泛用标志，与卡组关键技能/手牌相关 | 阶段检测必须 deck-specific，不能用回合数硬编码 |
| **C2** | 即使快攻也有展开期（辛焱例：0费圣遗物+庭院+武器启动） | 展开期检测 ≠ "是否在铺装备"，而是"关键组件是否就位" |
| **C3** | 混子位被击倒不构成阶段转换（迪希雅例） | 角色击倒不能统一视为重大事件，需区分功能权重 |
| **D2** | 操作顺序极其重要（琴音之诗+饰金之梦例） | 操作序列必须作为搜索对象，不能只看集合 |
| **D4** | Step-level 对胜负影响最大（对人类），但 AI 需先有 Game-level | **分层架构是必须的，不是可选的** |
| **E2** | 同一卡组在不同对局走不同胜利路径（火刻例） | Game-level 策略必须是条件性的，不是固定的 |
| **F1** | 读牌是关键决策依据，不是锦上添花 | 隐藏信息建模不应推迟到"后续版本" |
| **critical-gaps 1.3** | 节奏应拆解为子指标（骰效、行动密度、对手强制响应） | 移除"节奏"作为独立概念，用可度量指标替代 |
| **critical-gaps 2.2** | minimax + 强先验降低计算量 | 对手建模方向：不是 self-play 对称假设，而是 minimax + 先验剪枝 |

### 18.3 更新后的改进路线

#### P0：Game-level 策略注入 + Observation 落地（阻塞一切后续）

**目标**：让 AI 在做每一步决策时，至少知道"我这套牌要怎么赢"。

**具体措施**：

1. **Archetype 策略模板**：为每套卡组定义一个 `GamePlan` 结构，包含：
   - 胜利路径描述（如"T2-T3 爆发击穿"、"资源消耗 + 伺机点杀"）
   - 关键组件清单（哪些手牌/装备/状态是展开前提）
   - 展开完成条件（不是回合数，而是组件就位状态）
   - 条件路径分支（如火刻：对快攻可莉首发偏防守，对慢速班尼特首发偏进攻）

2. **ObservationV1 落地**：按 `rl-implementation-spec.md` 的 schema 实现，优先覆盖：
   - 原始状态层（角色/骰子/手牌/场面）
   - 合法动作上下文层（候选列表 + 费用 + 类型）
   - 中间特征层：展开完成度、骰子质量（对齐度而非数量）、功能层级

3. **Game-level 特征进入 observation**：
   - `展开完成度`：关键组件就位百分比
   - `当前阶段估计`：基于组件状态而非回合数
   - `胜利路径活跃度`：当前主路径是否仍可行

**验收标准**：AI 在选择操作时，能区分"展开期应该铺装备"和"执行期应该输出"。

#### P1：操作序列搜索 + 反应链先验（Step-level 质量提升）

**目标**：在 Game-level 锚定后，提升单步决策质量。

**具体措施**：

1. **Value-guided beam search 激活**：
   - 当前 gi-agent 的 `BoundedSearcher` 默认关闭（`searchDepth=0`）
   - 用 P0 的中间特征作为搜索启发函数
   - 搜索深度先设为 2-3 步（覆盖"调和→技能→切人"级别的序列规划）

2. **反应链模板库**：
   - A4 明确表示反应链是有意识设计的，但搜索很难找到
   - 为常见反应组合（扩散+双超导、挂元素→蒸发/融化等）建立先验模板
   - 搜索时优先展开匹配模板的操作序列

3. **骰子规划子问题**：
   - B3 明确"向前看 ≥ 2 次行动"是常态
   - 骰子分配作为搜索的**预处理约束**（而非事后验证）
   - 先验：调和在回合早期执行（B2 回答确认）

4. **操作顺序敏感的候选排序**：
   - D2 明确操作顺序导致完全不同结果
   - 候选排序模型必须以序列上下文为输入，不能独立评分

**验收标准**：在固定 matchup 上，搜索版 vs 无搜索版胜率显著提升（≥5%）。

#### P2：非线性模型 + 阈值特征（突破线性天花板）

**目标**：当前 gi-ml 全部使用线性模型，无法表达框架中反复强调的阈值跳变。

**具体措施**：

1. **模型升级**：
   - 将 `SlotLinearRanker` / `LinearValueModel` 替换为 GBDT 或浅层 MLP
   - critical-gaps 2.1 确认：价值函数是"平滑基线 + 若干阶跃叠加"的混合体
   - 阈值跳变（能量满、斩杀线、召唤物计数）需要非线性模型才能捕获

2. **阈值特征工程**：
   - 从 critical-gaps 2.1 提取的具体阈值：
     - 能量 `max_energy - 1 → max_energy`：大招解锁
     - 能量 `1 → 2`：追忆之注连增伤解锁
     - 血量 `≤ 6`：狼的末路额外 +2 伤
     - 召唤物可用次数 `> 3`：八重神子额外触发
   - 这些阈值作为二值/多档位特征直接输入模型

3. **功能层级特征**：
   - 框架 14.3 定义了核心/战术/残余三层功能
   - critical-gaps 1.2 确认了操作集 + 阈值的形式化方向
   - 将每个角色的功能层级作为离散特征输入

**验收标准**：非线性模型在相同数据量下，branch-eval 排序准确率显著优于线性模型。

#### P3：条件路径 + 对手建模（Turn-level / Game-level 动态化）

**目标**：处理 E2 揭示的"同一卡组不同路径"问题，以及 F1 揭示的"读牌是关键决策依据"。

**具体措施**：

1. **条件 GamePlan**：
   - P0 的 GamePlan 是静态模板，P3 使其动态化
   - 基于对手阵营（E2：看到对方阵营即可触发路径切换）和对局进展切换策略
   - 模型学习"在什么条件下切换路径"

2. **对手建模（minimax + 先验）**：
   - critical-gaps 2.2 确认方向：minimax + 强先验降低计算量
   - 用对手 archetype 先验（从阵营推断）初始化对手模型
   - 搜索中使用 minimax 而非 self-play 对称假设
   - 对手行为随对局进行逐步更新（贝叶斯后验）

3. **隐藏信息建模**：
   - F1 明确读牌是关键决策依据
   - 基于已打出/调和牌的信息 + 牌库剩余 + 对手行为模式
   - 先用 framework.md def 0 的概率上界公式作为基线
   - 将对手手牌概率估计作为特征输入 observation

**验收标准**：在非对称 matchup（快攻 vs 控制）上，条件路径版 vs 固定路径版胜率显著提升。

#### P4：在线 RL 微调（仅在 P0-P3 骨架稳定后）

**目标**：在前述结构全部就位后，通过 RL 微调提升策略精度。

**具体措施**：

- 按 17.9-17.10 已定义的 reward / training protocol 执行
- 终局奖励为主，dense shaping 先只开通用项
- self-play 对手池：镜像 40% + 历史 checkpoint 40% + baseline 20%
- 验收：对固定 baseline 胜率 ≥ 54%，对任一关键 baseline 不退化超过 2%

### 18.5 优先级依赖图

```
P0 (Game-level + Obs)
 ├── P1 (搜索 + 反应链先验)
 │    └── P2 (非线性模型 + 阈值)
 │         └── P3 (条件路径 + 对手建模)
 │              └── P4 (RL 微调)
 └── P2 可与 P1 并行（模型升级不依赖搜索）
```

P0 是唯一的硬前置。P1 和 P2 可以并行。P3 依赖 P1（搜索基础设施）和 P2（非线性模型能力）。P4 依赖全部前置。
